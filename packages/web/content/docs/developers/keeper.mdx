---
title: Keeper
description: The script that moves loans along and harvests pay-down rewards on a schedule, for both pairs, what one pass does, and how to run it yourself.
---

The keeper moves Doji loans along when their time comes, for the 20 October pair and the Wave 2 pair side by side. Each pass looks at every open loan and every loan date on Mezo testnet and makes the one call each is ready for: it starts an auction on a loan that is overdue or unsafe, cancels an auction on a loan that is safe again, prepares and settles a position nobody bought, and closes a loan date once all of its loans have ended, so lenders can redeem. It also checks that Mezo's sMUSD vault would hand back the lender money parked in it, and it harvests the pool rewards of positions that named PayDown into repayments of their loans.

Anyone can run it. Every call it makes is open to any wallet, and the contracts re-check every condition themselves, so a keeper that is wrong, late or hostile can waste its own gas but cannot move anyone's money. The keeper wallet has no role in the contracts, gives no approvals and never holds MUSD: a harvest pays the borrower's loan and sends the rest to the borrower, never to the caller. It only needs a little test BTC for gas.

The code is in [packages/keeper](https://github.com/ramakrishnanhulk20/doji/blob/main/packages/keeper/README.md).

## Two pairs, never mixed

A pair is one LoanManager and its CreditMarkets, plus PayDown and UnitMarket from Wave 2 on. Each pair has its own deployment record, and the keeper reads the list in `DEPLOYMENT_FILES`: by default `31611.json` (20 October) and, when it exists, `31611-wave2.json`. The two pairs share maturities and position ids, so the keeper never identifies a loan, date or harvest by its id alone. Every object is read from and written to the contracts of the record it came from, and every line it prints starts with that record's name (C49). Two records that name the same Doji contract stop the run before anything is read.

## What one pass does

1. Reads every record in `DEPLOYMENT_FILES` and refuses to run unless the RPC is Mezo testnet (chain 31611) and, for each pair, LoanManager, CreditMarkets and veBTC on chain match the record and each other, PayDown serves that LoanManager, UnitMarket lists that CreditMarkets' units, and the savings vault the record names is the one CreditMarkets reports. If the keeper's key is the owner, pending owner or guardian of any LoanManager, CreditMarkets, PayDown or UnitMarket, or the treasury of any CreditMarkets or UnitMarket, a live pass stops before it simulates or sends anything; a dry run prints a warning.
2. Checks the vault. For each pair whose CreditMarkets has MUSD parked in Mezo's sMUSD vault, it simulates, as CreditMarkets itself, a vault `withdraw` of the whole `parkedPrincipal`. That sends nothing and costs nothing. If the vault would refuse, or the check cannot be made, it prints a line starting `VAULT ALERT:`, finishes every other job, prints the alert again as the last line and exits with code 3 (C35). This runs before anything that could stop the pass.
3. For each pair, finds the open loans from LoanManager's `Borrowed` and `LoanClosed` events since that pair's deployment block: a position is open when its latest `Borrowed` comes after its latest `LoanClosed`. The events come from Mezo's block explorer API, topped up from the RPC for the newest blocks. If the explorer fails or is far behind, the RPC alone reads the last 64 pages of 10,000 blocks (about 35 days) and the pass warns that older loans are not seen this run. The events are only hints: each loan is read from the contracts before anything is decided.
4. For each open loan it reads the loan, its auction, `isOverdue` and `isUnsafe`, and picks at most one action:

| Action | When |
| --- | --- |
| `startAuction` | The loan is active and overdue or unsafe. |
| `cancelAuction` | The loan is in an auction that began on or before its due date, and it is safe again. |
| `prepareSettle` | Unsold past floor time, overdue or unsafe, the position has a standing vote or a permanent lock, and the epoch's first hour has passed (Mezo refuses vote resets in that hour). |
| `settle` | Unsold past floor time, overdue or unsafe, the lock has ended and there is no vote. |

5. Checks the 32 most recent weekly loan dates of each pair. For each one it compares the chain's own count of open loans (`marketOf(date).openLoans`) with what the scan found. If the chain has more, it prints a warning, acts on what it found, and exits with code 2 so the run shows red. It calls `finalize` on a date once the date has passed, it had loans, none is still open and it is not closed yet.
6. Harvests, only after every pair's loan and date jobs have run (C48). If a pair's jobs stopped, or `MAX_ACTIONS` ran out, it skips every harvest this pass and says why, so rewards never take gas the loan jobs still need. For each pair that has a PayDown:
   - It reads PayDown's pause switch and the BTC price; a paused PayDown or an unavailable price skips the pair with a line saying so.
   - It finds the positions whose latest `RewardOperatorSet` event names this pair's PayDown, and reads each again with `positionOf`. A position whose operator is no longer PayDown, or that LoanManager no longer holds, is skipped with that reason.
   - For each one it reads the pools the position votes for, each pool's gauge and its fee and incentive reward contracts, and lists only MUSD and BTC, only where that contract records the token as a reward (`isReward`), and only where something is earned. A claim lists at most 16 tokens; extra gauges wait for the next harvest.
   - It skips a position whose earned MUSD plus earned BTC, valued at the price feed, is below `HARVEST_MIN_MUSD`. Otherwise it simulates `PayDown.harvest` and sends it only if the simulation passes. PayDown decides what is sold and at what floor.

   Pool rewards arrive once a week when the epoch turns, and a harvested position reads zero earned until the next one, so the harvest step runs every pass but acts about once a week per position.
7. Simulates every call first and sends it only if the simulation passes. A refused simulation is logged with its reason and skipped.

## Bounds on one run

| Bound | Limit |
| --- | --- |
| Deployment records | 4 |
| Open loans read per pair per pass | 150, the ones due first |
| Loan dates checked per pair | 32 |
| Explorer calls per event type | 20, at 1,000 events each |
| RPC log pages when the explorer is down | 64, of 10,000 blocks each |
| Loan and date transactions per pass, across all pairs | `MAX_ACTIONS`, 10 by default, at most 50 |
| Positions read for a harvest per pass, across all pairs | `HARVEST_MAX_POSITIONS`, 10 by default, at most 20; with more candidates the window moves every 30 minutes |
| Reward tokens per harvest | 16 |

An RPC request that is rate limited or times out is retried once. If it fails again, that pair's jobs stop, because acting on a partial list would quietly skip loans. The other pair still runs, harvests are skipped, and the pass exits 1.

## Run it on your machine

Needs Node 20.12 or newer.

```bash
cd packages/keeper
npm ci
npm run keeper:dry   # one pass that only simulates; needs no key and sends nothing
npm run keeper       # one pass that sends; needs KEEPER_PRIVATE_KEY
```

It prints one line per decision, each starting with the record it belongs to, for example:

```text
31611       market 2026-10-22      finalize       matured and every loan closed | simulated
31611-wave2 vault check            simulate       simulated withdraw of 10 MUSD parked principal by CreditMarkets <address> from vault <address> | succeeds
31611-wave2 harvest 412            skip           0.004 MUSD and 0 BTC earned, worth 0.004 MUSD, below HARVEST_MIN_MUSD 0.01 | -
```

| Setting | Default | What it is |
| --- | --- | --- |
| `KEEPER_PRIVATE_KEY` | none, required unless dry | A wallet that holds a little test BTC for gas. Give it nothing else. |
| `MEZO_TESTNET_RPC` | `https://rpc.test.mezo.org` | Mezo testnet RPC. |
| `MEZO_TESTNET_EXPLORER_API` | `https://api.explorer.test.mezo.org/api` | Mezo testnet explorer API, for the `Borrowed`, `LoanClosed` and `RewardOperatorSet` events. |
| `DEPLOYMENT_FILES` | `../contracts/deployments/31611.json`, plus `../contracts/deployments/31611-wave2.json` when that file exists | Comma-separated deployment records, one per pair, at most 4. A record that is named but missing stops the run. The old single-record `DEPLOYMENT_FILE` is refused with a message to rename it. |
| `MAX_ACTIONS` | `10` | Most loan and date transactions one pass sends across all pairs, 1 to 50. |
| `HARVEST_MAX_POSITIONS` | `10` | Most opted-in positions one pass reads for a harvest across all pairs, 0 to 20. 0 turns harvests off. |
| `HARVEST_MIN_MUSD` | `0.01` | A position is harvested only when what it has earned is worth at least this many MUSD. |
| `VAULT_CHECK_OVERRIDE` | none | A test hook read from the environment only: it points the vault check at another contract so you can watch the alert fire. Never set it on GitHub. |

Any setting not in the environment is read from `packages/contracts/.env` if that file exists; nothing else from that file is loaded.

To see the vault alert fire without touching the vault, point the check at the MUSD token, which has no `withdraw`:

```bash
DEPLOYMENT_FILES=../contracts/deployments/31611.json,../contracts/deployments/31611-wave2.json \
VAULT_CHECK_OVERRIDE=0x118917a40FAF1CD7a13dB0Ef56C86De7973Ac503 npm run keeper:dry; echo "exit $?"
```

It prints a `VAULT ALERT:` line for the Wave 2 pair, as long as it has MUSD parked, and ends with exit code 3.

Exit codes:

| Code | Meaning |
| --- | --- |
| 0 | The pass finished, even if some simulations were refused. |
| 1 | A setting is missing, a record or the chain does not check out, a live pass found the key holds a role, a pair's jobs stopped, or a sent transaction failed. |
| 2 | A checked date has more open loans on chain than the scan found, or could not be checked. |
| 3 | A vault check raised a `VAULT ALERT`. |

When more than one applies, 1 wins over 3, and 3 over 2. A dry run exits 2 and 3 the same way.

## Run it on GitHub

[.github/workflows/keeper.yml](https://github.com/ramakrishnanhulk20/doji/blob/main/.github/workflows/keeper.yml) asks for one pass every 30 minutes and runs one whenever it is started by hand, with `DEPLOYMENT_FILES` naming both records. GitHub starts scheduled jobs late on a quiet repository, so from 19 to 22 October 2026 the scheduled passes came 2.3 to 5.9 hours apart (median 4.7). A call that cannot wait, such as starting the auction of a loan that turned unsafe, can be made by anyone at once from the loan's page.

- It runs only on a schedule or by hand, never for a pull request, so code from someone else's branch never sees the key. A manual run from any branch other than `main` is skipped.
- The job has a read-only token, actions pinned to exact commits, `npm ci --ignore-scripts` so no install script runs, a 10-minute timeout, and one run at a time.
- The key is a repository secret named `KEEPER_PRIVATE_KEY`. A `MEZO_TESTNET_RPC` secret can replace the public RPC.
- A `VAULT ALERT` makes the run fail, and GitHub emails a failed scheduled run to the person who set up the workflow when their workflow emails are on.

## Gas

Measured on a fork of Mezo testnet; at the 172 wei per gas testnet charged on 2026-10-19, each costs about 0.0000000001 test BTC or less:

| Action | Gas |
| --- | --- |
| `startAuction` | about 119,000 |
| `cancelAuction` | about 71,000 |
| `prepareSettle` | about 301,000 |
| `settle` | 410,000 to 614,000 |
| `finalize` | about 76,000 |

The vault check is a simulation, so it costs no gas. A `PayDown.harvest` measured by the test suite has a median of about 604,000 execution gas, from 32,116 to 682,066 (the [README's gas table](https://github.com/ramakrishnanhulk20/doji#gas)); the real reward contracts and the real pool cost more, and no live harvest had run when this page was written.

## What it does not do

It does not buy auctioned positions, write off loans whose position left custody, mint, sell or redeem credit units, or claim anything for itself: those belong to the people they concern. Its harvest lists only MUSD and BTC, only from the pools a position votes for now; other reward tokens are left for the borrower to claim, or to sell with their own minimums through `harvestAndSwap`. It never sells anything itself. It has no power the contracts do not give every wallet, and its uptime is best effort. If it is down, anyone can make the same calls, from this script or from a loan's own page.
