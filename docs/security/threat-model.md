# Doji threat model

Written at the architecture gate on 2026-10-16, before any contract code, following the threat model pass in our build method (taken from the Monad Foundation's "Writing secure code with LLMs"). The system was described in plain functional terms first; an independent reviewer produced sections A, B and C from that description, in two passes: one for a pooled-vault design, then a full second pass for the fixed-term credit-market design we chose. Section C is the definition of done: a contract is finished only when every invariant in C is upheld and a test shows it.

**What Doji is.** Holders of veBTC (Mezo's vote-escrow Bitcoin position, an ERC-721) hand the position to `LoanManager` and borrow MUSD for a fixed term at a fixed rate from lenders who post offers in `CreditMarkets`. Each loan date ("maturity") is a Thursday 00:00 UTC and is its own market. Lenders receive ERC-1155 credit units for that date (one unit is one MUSD due on that date), which they can transfer. A loan that becomes unsafe or goes unpaid is sold in an auction; if nobody buys, the lenders receive the Bitcoin itself. A keeper script that anyone can run triggers resolutions. The contracts cannot be upgraded. There is no database and no server endpoint that takes user input.

**Context we do not hide.** On 2026-10-05 an attacker moved 37 veBTC positions on Mezo mainnet through a trusted-forwarder (meta-transaction) sender-check flaw (https://mezo.org/blog/incident-report-october-5-2026). Meta-transactions on veBTC are now disabled. A contract that holds many veBTC positions concentrates exactly that kind of risk, which is why custody comes first below.

## A) App-class risk profile

Class: a custodial fixed-term credit market. It runs an order book that escrows lender MUSD and issues transferable claims (ERC-1155 credit units) that redeem pro rata from a per-maturity pool. It holds other people's bearer collateral (veBTC NFTs) and acts as their owner toward Mezo contracts. It prices loans with an external oracle and lets anyone force-sell or wind down collateral. Four sub-classes stack: an escrow order book; an issuer of claim tokens with pro-rata, loss-sharing redemption; a custodian acting as owner for many users (confused-deputy territory); and an oracle-priced liquidation engine that anyone can trigger.

- **A1 Collateral identity and custody.** The NFT enters by `deposit` (pulled with `transferFrom`) or `lockAndDeposit` (minted to `LoanManager` by `createLockFor`, so there is no prior owner). A plain transfer in by someone else runs no hook and must never create a position. `onERC721Received` hands over an operator, a `from` and free-form data, and only `from` is the prior owner.
- **A2 Collateral that changes or leaves without the custodian acting.** Grant managers can revoke and move grant NFTs. Managed escrows let depositors pull value out. veBTC is a proxy Mezo can upgrade. The 2026-10-05 forwarder incident shows that one sender-check flaw moves NFTs without the owner, and holding every NFT in one address turns one such flaw into a loss for every maturity at once.
- **A3 Valuation, parsing and clock mismatch.** Borrow, roll and liquidation read `locked()` and `fetchPrice()`. `locked()` returns 3 fields on testnet and 4 on mainnet, the amount is a signed int128, a permanent lock reports `end = 0`, and voting power decays and is not the locked BTC. Offer maturity, loan maturity, lock end and epoch are compared against each other, and seconds to maturity sit inside the face formula. If any two go through different arithmetic, a loan can outlive its lock, roll after default, or owe a different face from the units minted for it.
- **A4 Oracle dependence.** A stale or zero price must stop borrowing. The same price starts both kinds of auction and splits the Bitcoin in settle, so an oracle outage stalls resolution and the market's finalisation. MUSD = 1 USD is assumed and never checked.
- **A5 Liquidation economics.** The sale starts at collateral value and falls to a floor. In a thin market the only bidder may be the borrower or a friend. An auction on a loan that recovers must not keep running on an old start value.
- **A6 Confused deputy.** Every Mezo contract trusts `LoanManager` as owner of every NFT at once. One missing per-token check in a pass-through (vote, reset, poke, claimFees, claimBribes, claim, increaseUnlockTime) lets anyone act on another user's NFT. `claimFees` and `claimBribes` take reward-contract and token addresses chosen by the caller, so attacker code runs in the middle of `LoanManager`'s call.
- **A7 Reentrancy, receiver hooks and balance deltas.** Minting ERC-1155 units would call the maker's `onERC1155Received` in the middle of a borrow or roll. NFT transfers out, BTC paid out and reward forwarding hand control to outside code mid-update. `LoanManager` holds claimables at rest, so forwarding by raw balance would sweep them, and a measured delta can still catch another position's BTC if a third party can make Mezo pay `LoanManager` during the call.
- **A8 Claim-token accounting.** Units are a pro-rata claim on a per-maturity pool of MUSD and, after a settle, BTC. When units differ from debt, a fully repaid market redeems below 1 or leaves funds stuck. Escrow and every market's collected funds share one balance, so a bookkeeping slip moves money between makers and maturities. If the open-loan counter drops twice the market finalises early; if it never drops the market freezes. Losses at a maturity are shared by every unit there, including units from loans a lender never chose.
- **A9 Liveness.** One unresolved loan blocks a whole maturity. A vote in the lock's last epoch blocks the reset. A permanent lock needs a reset, `unlockPermanent` and up to 28 days. `increaseUnlockTime` lets a borrower push the lock end out before defaulting. A stale oracle stops auction starts and settle. A hostile maker hook, a recipient that reverts, unbounded arrays or a pause that blocks roll can each stop a flow.
- **A10 Privileged roles.** If the owner could change the liquidation line, curve or fee on live loans, it could hurt borrowers or lenders. A pause that stops repay, cancel or redeem traps users. Because the contracts are immutable, no admin can replace code; the cost is that a bug or a Mezo change (for example to `locked()`) cannot be fixed in place, and the only answer is to pause new risk and launch a new deployment that users move to themselves.
- **A11 Approvals and signatures.** A function that pulls from an arbitrary `from` spends a victim's standing approval. A front-run permit makes honest calls revert. A UI that asks for `setApprovalForAll` on veBTC or on credit units exposes every NFT or every maturity the user holds.
- **A12 Off-chain.** The keeper and the web app read a public RPC and sign. With no database, the UI rebuilds the offer book from events, so spam offers, hostile contract makers and offers cancelled in the same block all reach the borrower's transaction. Reward token names are strings an attacker picks. Signing on the wrong chain (31611 versus 31612) or against a wrong address book sends assets to the wrong place. GitHub Actions secrets leak if pull-request code runs with them.
- **A13 Order-book races.** A maker can cancel ahead of a fill, another borrower can take the same offer, and a borrow can cite an offer from a different maturity. Each of these must revert, and none may fill on different terms.

Not applicable: SSRF; SQL, command or template injection; file upload; path traversal; sessions and cookies; multi-tenant database isolation. There is no database, no server endpoint that takes user input and no stored user content. (True of Wave 1. Quests add two endpoints and a server-rendered image, and SSRF then applies in a narrow form: see A36.) Per-tokenId and per-maturity isolation inside the contracts stand in for tenant isolation (A6, A8). On-chain price manipulation does not apply: the price comes from the Skip oracle, not from a pool this system reads, and Doji never swaps on a DEX. Bridging is out of scope.

## B) Threat model

**Trust boundaries**
- T1 Any EOA or contract calling `LoanManager` or `CreditMarkets`, including `onERC721Received`.
- T2 Answers from Mezo contracts: veBTC (`locked`, `ownerOf`, escrow type, `grantManager`, voted state, minted tokenId), PriceFeed, PoolsVoter, BoostVoter, the fee distributor.
- T3 Outside code our contracts call or pay: reward contracts and tokens, ERC-1155 receivers, and contract recipients of NFTs, BTC or MUSD.
- T4 `LoanManager` and `CreditMarkets`: each takes the other's numbers (fills, faces, credits) as fact.
- T5 Mezo governance: the code behind the veBTC proxy can change.
- T6 The owner, guardian and treasury keys.
- T7 Mempool and block producer: transaction order, timestamps, the maturity instant, epoch edges.
- T8 Public RPC feeding the keeper and UI; GitHub Actions feeding the keeper; npm and Vercel feeding the bundle; the UI feeding the user's wallet.

**Attacker-controlled inputs**
- Direct: tokenId; offer maturity, APR and amount; `offerIds[]`, `amounts[]`, `maxAPR` and maturity in borrow and roll; repay amount and target tokenId; lock amount and duration; `pools[]`, `weights[]`, `rewardContracts[]`, `tokens[][]`; purchase `maxPay` and deadline; redeem amounts; unit transfers; NFT transfer operator, from and data; permit fields; `msg.value`; `msg.sender` being a contract with ERC-721, ERC-1155 or token hooks; timing relative to the keeper, the maturity instant, the epoch flip and the lock end.
- Indirect: what `locked()` returns (layout, sign, permanent flag, and end, which the borrower can push out with `increaseUnlockTime`); `ownerOf`; escrow type; grant manager; voted state; lock amount (`depositFor` is open on normal positions); price value, decimals and freshness; how reward contracts and tokens behave; permissionless Mezo calls that pay `LoanManager` as owner; the offer book (hostile contract makers, offers cancelled in the same block); unsolicited MUSD, BTC, units or tokens; stored values read back later (borrower, maturity, face, repaid, open-loan count, collected, auction snapshot, claimables, a returning tokenId's leftovers); owner parameters; RPC answers and event logs; token names; the wallet's chain ID.

**Privileged position and assets**
- `LoanManager` owns every collateral NFT and so all locked BTC. It is the only address Mezo accepts to vote, reset, extend, claim, `unlockPermanent` or withdraw them, so one veBTC sender-check flaw reaches all of them at once.
- `LoanManager` is the only caller that can open loans against escrowed offers and credit a market, so it decides what each market is owed.
- `CreditMarkets` holds every maker's unfilled MUSD and every maturity's collected MUSD and BTC in one balance, and it is the only minter of units. Isolation between maturities is bookkeeping, not separate contracts.
- `LoanManager` holds borrower claimables (auction surplus in MUSD, settle leftovers in BTC) between transactions.
- The owner controls parameters and the treasury address; the guardian controls pause; the treasury receives fee units and penalties. The keeper key holds gas only. The UI decides which offers, transactions and approvals users are asked to sign.

**Attacker goals**
- G1 Borrow more than the collateral is worth, then walk away: misdecoding `locked()` across chains, valuing by voting power, a grant or managed NFT losing value or leaving custody, price decimals, a maturity past the lock end, a raised maxLTV.
- G2 Take another user's NFT or funds: claiming a raw-transferred NFT, a pass-through or `withdrawCollateral` without a borrower check, two endings both completing, a stale record on a returning tokenId, a reward delta that includes another position's BTC, a claimable paid twice, a veBTC flaw.
- G3 Strip borrower equity: a sale on a stale start value, an auction started on a price dip, a curve or penalty changed mid-auction, liquidating a permanent lock whose end reads 0, a pause that blocks a roll.
- G4 Take value from lenders and unit holders: a fill booked to the wrong maturity, units that exceed debt, re-entering cancel inside a fill, buying back one's own collateral below the debt, redeeming before final, finalising while a loan is open.
- G5 Freeze funds: one loan that never closes (oracle down, a vote in the last epoch, a lock pushed out), a hostile maker hook that reverts every fill, recipients that revert, unbounded arrays, a pause on exits.

## C) Defensive-programming standards (the definition of done)

### Custody and identity
- <a id="c1"></a>**C1.** Only the address that owned a veBTC just before it entered `LoanManager` can become its borrower: `msg.sender` for `deposit` (which pulls with `transferFrom` after a single-token approval) and for `lockAndDeposit` (which mints with `createLockFor`). Operator and data never set identity. An NFT that arrives any other way, or an `onERC721Received` call from anything but the veBTC proxy, never becomes a position. Test: Alice plain-transfers an NFT in; Bob tries every entry point and cannot claim it.
- <a id="c2"></a>**C2.** `LoanManager` accepts only NFTs whose value no third party can lower or remove: one positive test (normal escrow type and `grantManager(tokenId) == address(0)`), checked at intake and on every borrow and roll. If `ownerOf` stops being `LoanManager` while a loan is open, nothing that touches the position runs for that loan, and anyone can close it in one call as a write-off with zero recovery, so its market can still become final (C15). Repaying stays open, because paying a debt only adds to what that date's lenders collect.
- <a id="c3"></a>**C3.** `LoanManager` acts as owner only through the calls in this design. It gives no veBTC approval or approval-for-all, has no generic call or multicall, never calls merge, split or `lockPermanent`, and accepts no meta-transactions. Its only delegatecall target is the PassThrough library linked at deploy: deployed by the deployer before `LoanManager`, its address embedded in `LoanManager`'s code, its runtime code hash checked against the compiled artifact by the deploy (C22), stateless, unable to self-destruct on Mezo (SELFDESTRUCT is disabled since mezod v13), and run only inside `LoanManager`'s lock after the C4 check. Every call target except the reward contracts in C10 is fixed at deploy. The treasury is the only address the owner may change, and it can only ever receive fee units and penalties; penalties are credited to it as claimables it collects itself, so a treasury that refuses a token cannot block a sale or settle. Ownership cannot be renounced, so the C19 rescue paths always have an owner. The owner's two rescue functions are bounded in C19.
- <a id="c4"></a>**C4.** Every borrower action passes one shared check: the caller is the position's recorded borrower. `borrow` also needs the position held with no open loan. Every pass-through needs the position in custody and never runs while the loan is in auction, except `claimRewards` (L-01 of the 4 Nov audit): rewards are not collateral and the claim only pays the caller, so the borrower or the named reward operator may claim them during an auction, which keeps the borrower's earned rewards from passing to a buyer and lets a harvest repay, and so cure, the loan. `vote` and `extendLock` also need the loan to be None or Active, on time and safe at a fresh price, because they change what backs the loan. `resetVotes`, `claimRewards` and `claimRebase` run at any health, because they only clear votes or pay the borrower rewards that are not collateral. `roll` needs the loan Active and not overdue; a loan that is unsafe but on time may roll, because the new loan must pass maxLTV at a fresh price and the old debt is repaid in full in the same transaction. `withdrawCollateral` needs no open loan and sends the NFT only to the recorded borrower.
- <a id="c5"></a>**C5.** No vote is cast at or after `lockEnd - 1 week`, and the same applies to `poke` if poke counts as a vote. This guarantees a reset is available to settle when the lock ends. A vote cast before deposit, on PoolsVoter or on ValidatorsVoter (veBTC counts both through its secondary-voter list), is cleared by `prepareSettle`, which resets every voter that holds a live vote for the position; each needs a new epoch since that vote, which C26 allows for. A permanent lock may vote in any epoch, so its settle may wait one epoch for the reset; that wait counts toward C26's time limit.

### Valuation and terms
- <a id="c6"></a>**C6.** One function gives collateral value to borrow, roll, liquidation, settle, the keeper and the UI. It decodes `locked()` with the layout of the veBTC deployed on that chain and reverts on any other return size or on a zero or negative amount. It uses locked BTC, never voting power. A permanent lock is never expired, whatever `end` says. Test: fork tests on 31611 and 31612 against known tokenIds.
- <a id="c7"></a>**C7.** One function gives price: `fetchPrice()`, above zero, normalised to 18 decimals once. If it reverts or returns 0, then borrow, roll, both auction starts, purchase and settle all revert. Nothing runs on a cached price.
- <a id="c8"></a>**C8.** One quote function turns principal, APR, seconds to maturity and fee share into the fill's face, the maker's units and the treasury's units, with maker units plus treasury units equal to the face exactly. Interest accrues per second. A loan's debt is the sum of its fills' faces, fixed at origination; repayments reduce what is still owed, never the face. A borrow, and the borrow half of a roll, succeeds only if all of these hold: every listed offer is open, is for exactly this maturity, has an APR no higher than `maxAPR`, and fills for exactly the listed amount; the maturity is valid and open (C24) and no further away than the maximum term; for a normal lock the maturity is at or before the C6 lock end, and for a permanent lock it is within the maximum term; total face is at most maxLTV times value; principal is at least the minimum loan; the array cap (`MAX_FILLS` offers per loan) holds; the collateral passes C2. Every borrow entry point goes through this one internal path.

### Resolution
- <a id="c9"></a>**C9.** A position (custody and borrower) and its loan (maturity, face, repaid, state) are separate records. A loan is Active, Auction or Closed, and exactly one ending completes: full repayment (including by roll), purchase, settle, or the C2 write-off. A loan is Closed in the same transaction that pays its last debt, and its market's open-loan count falls exactly once. The loan record is deleted on close and the position record when the NFT leaves, so a returning tokenId starts empty. Repaying in full during an auction ends the auction, and the NFT stays in the borrower's position.
- <a id="c10"></a>**C10.** Reward forwarding runs under a reentrancy lock and pays the borrower exactly the increase in `LoanManager`'s balance of each listed token, measured around the claim. The borrower names gauges, never reward contracts: the fee and incentive contracts are looked up from PoolsVoter (`gaugeToFees`, `gaugeToBribe`) for a gauge PoolsVoter has registered, and every listed token must be one that the contract on its own side lists as a reward (`isReward`, F36; the 20 Oct contracts used PoolsVoter's whitelist instead). So the trust root is PoolsVoter's gauge creation: the only code that runs during a claim is Mezo's own reward contracts paying this tokenId and the reward tokens' own transfer and balance code, and MUSD and BTC rewards, which most pools pay, are forwarded in full. The most a reward token with transfer callbacks could steer into a measured window is the fee distributor's BTC for an expired lock that LoanManager holds. Claimables never change during the call, so a measured increase can never include another user's funds. A token that a stranger can make Mezo pay to `LoanManager` in a separate transaction (the fee distributor's claim on an expired lock) is not credited to anyone (a stated non-goal). The borrower's own `claimRebase` is measured and credited to that tokenId's borrower only.
- <a id="c11"></a>**C11.** Let P be the price paid and D the debt still owed. A purchase pays the market min(P, D), the treasury min(penalty x D, P - min(P, D)), and the borrower the rest as a claimable; the three always sum to P. The price follows the curve snapshotted at auction start: the C6 x C7 value at start, falling linearly to the C29 floor over the duration, then flat. Every purchase also reprices at a fresh value: P = max(curve, the C29 floor recomputed at the value now), so a purchase reads the oracle, overdue auctions included. P can therefore rise within a block: anyone can add BTC to a normal lock with `depositFor`, which raises the value now. That only ever raises what the market and the borrower receive, and buyers set `maxPay` with slack (C21). A purchase needs P at most `maxPay` and the deadline not passed. Every step that ends or irreversibly changes a loan (purchase, `prepareSettle`, settle) needs the loan overdue (now > maturity) or unsafe at a fresh price. An auction started while the loan was on time (an LTV auction) sells only while a fresh price shows it unsafe, even after maturity passes; if a fresh price shows it safe, anyone can cancel it, even past maturity, and the next trigger starts a new auction from a fresh value. An auction started after maturity (an overdue auction) can never be cancelled, so a loan restarts at most once. `prepareSettle` may run on an unsafe LTV auction before maturity once its floor time has passed. This is deliberate, because the borrower has had the whole auction to repay, and it is not reversed if the loan later recovers: a permanent lock stays a normal lock of the maximum length and that epoch's votes stay reset.
- <a id="c12"></a>**C12.** `settle` runs only when the auction is past its floor time unsold, the lock has ended, and the loan is overdue or unsafe at a fresh price (C11). For a permanent lock, the reset and `unlockPermanent` steps can be called by anyone once the floor time passes. Settle withdraws the BTC and never swaps on any DEX. BTC received is the change in `BTC.balanceOf` around `withdraw`, never `locked().amount`. With V the BTC received valued by C7, the market receives BTC worth min(D, V), the treasury receives BTC worth min(penalty x D, V - min(D, V)) as a BTC claimable, and the borrower receives the rest as a BTC claimable; the three always sum to the BTC received. Afterwards `LoanManager`'s BTC is its claimables plus any stray BTC (C18), which nobody is credited.
- <a id="c13"></a>**C13.** Anyone can move an overdue or unsafe loan to Auction, and no single party can stop a resolution. The auction never depends on vote state. NFTs leave by `transferFrom`, never `safeTransferFrom`. No outside code runs inside a resolution (C23). Payouts to users are claimables. Caller arrays are capped. No on-chain loop runs over loans, offers, markets or holders.

### Credit markets
- <a id="c14"></a>**C14.** For each maturity, units issued (makers plus treasury; minted, pending, moved into Claims or redeemed) equal the sum of faces of the loans opened in it. A market's collected MUSD and BTC only increase, only by amounts measured arriving from `LoanManager` for a loan of that maturity. Across `CreditMarkets`, MUSD held is at least the open offers' unfilled amounts plus every market's collected MUSD minus paid out (redeemed or withdrawn early), and BTC held is at least every market's collected BTC minus paid out. Escrow pays out only through cancel and fills; collected funds pay out only through redemption and early withdrawal (C15). No accounting reads raw balances, so a donation changes nothing. Test: fuzz posts, fills, cancels, repays, rolls, purchases, settles and redemptions across several maturities, and assert all of these after every step.
- <a id="c15"></a>**C15.** A market becomes final only when its maturity has passed (C24) and its open-loan count is 0; after that nothing can add a loan to it. Redemption works only after final: it burns units from `msg.sender` only, first, then pays units x musdAtFinal / faceTotal plus units x btcAtFinal / faceTotal, all fixed at finalisation and rounded down; faceTotal counts every unit ever issued at the date, including units already moved into Claims. Once the date has passed, a holder may also move units into a non-transferable Claim with `withdrawCollected` and take its share of what has been collected so far: min(units, units x collected MUSD / faceTotal) and units x collected BTC / faceTotal, recomputed on the Claim's whole history, and again as more arrives. faceTotal cannot change after the date, so the share only grows, no holder gains by withdrawing first, and a unit receives the same total whichever path or timing, within rounding. Units moved into a Claim can no longer be sold. The MUSD part never exceeds 1 per unit, and paid out (redeem plus withdrawals) never exceeds collected.
- <a id="c16"></a>**C16.** An offer's maker, maturity and APR never change after posting, and offer ids are never reused. Posting pulls exactly the amount from `msg.sender` and needs a valid, open maturity within the maximum term (C24), an APR under a hard-coded cap, and an amount at least the minimum offer. Only the maker can cancel, at any time, for exactly the unfilled remainder; no market state or pause can block a cancel. Only `LoanManager` can fill, and a fill cuts the remainder before any other step. For a parked offer the yield is booked first from a read-only call to the vault's index, then the remainder is cut, both before any call that can change state (C33).

### Funds in and out
- <a id="c17"></a>**C17.** Funds are pulled only from `msg.sender`. Repay pulls at most the debt still owed. Roll pulls its top-up only from the borrower. A front-run permit cannot fail a call whose allowance already covers it. `lockAndDeposit` leaves no BTC allowance behind, and the minted tokenId is confirmed as owned by `LoanManager` before it is recorded.
- <a id="c18"></a>**C18.** No function is payable. If `veBTC.withdraw` pays by a native call (fork test), `receive()` exists and credits nobody; otherwise there is none. Stray BTC (native or ERC-20), MUSD, units or tokens sent to either contract never become anyone's claimable, any market's collected balance or any offer's escrow.

### Governance and off-chain
- <a id="c19"></a>**C19.** The guardian's pause stops only posting offers, opening new loans and lock creation, checked in the internal path those calls share. Roll is never paused: it only takes offers already posted, and blocking it would push honest borrowers into default. While borrows are paused a roll may refinance or top up but may not pay out new MUSD, because that is new borrowing against the collateral the pause protects. The following can never be paused either: cancel, repay, `withdrawCollateral`, auction start, purchase, the reset and `unlockPermanent` steps, settle, finalise, redeem, claims and pass-throughs. Setters keep 0 < maxLTV < liqLTV < 100%, and keep penalty, fee share, APR cap, floor, duration, maximum term, minimum loan, minimum offer and caps inside hard-coded bounds. maxLTV, liqLTV, fee share, auction floor, penalty and duration are snapshotted per loan when it opens or rolls (a roll is a new loan on that day's terms), and each auction copies its loan's terms; a change touches only new offers and loans. The guardian sets no parameters. Ownership moves in two steps and cannot be renounced. The maximum term is at most 4 weeks, within veBTC's 28-day maximum lock, so a permanent-lock loan can never outlive the lock `unlockPermanent` leaves. The admin surface is these setters, `CreditMarkets.setURI` (the units' metadata link, which moves no money), plus two rescue functions: `rescueToken` moves an ERC-20 only above what is recorded for users (for MUSD and BTC in `LoanManager`, only above the claimable totals; in `CreditMarkets`, never MUSD or BTC), and `rescuePosition` moves only a veBTC that `LoanManager` holds with no position record. The contracts are immutable, and if Mezo changes veBTC the only response is to pause new risk and launch a new deployment that users move to themselves.
- <a id="c20"></a>**C20.** The contracts re-check every condition the keeper or UI acts on. The keeper key holds gas only, and the keeper refuses to send anything when its key is the owner, pending owner, guardian or treasury of either contract. Its workflow runs only on main and never runs code from forks or pull requests. It acts on the open loans: a position whose latest `Borrowed` comes after its latest `LoanClosed`, counted from the deployment block, listed by the block explorer as a hint and by the RPC for the blocks the explorer has not indexed yet; when the explorer is down or more than 64 pages behind, the RPC reads only the last 64 pages and the completeness check below is what makes a missed loan loud. For every date it compares the chain's own open-loan count (`marketOf`) with what it found, and a run that finds fewer fails loudly after acting on what it has. Its loops are bounded per run (150 open loans, 32 dates, 20 explorer calls per event, 64 RPC pages), and writes are capped. It simulates every call before sending it.
- <a id="c21"></a>**C21.** The UI reads value, debt, face, the auction price and each loan's own auction terms from the contract views behind C6 to C8, C11 and C15, never the current settings. A figure with no view (the BTC price at the auction line, the split of a sale, a lender's withdraw and redeem amounts) is computed with the same formula and rounding as `Resolution` and `CreditMarkets`, and the contract decides: every write is simulated with the connected account before the wallet is asked. For ten minutes after the page sees a confirmation, a failed simulation or gas estimate is asked again for up to 90 seconds and the estimate is passed to the wallet, so a step is never refused for a node state older than the receipt it follows. A confirmation's logs come from a complete receipt, from the RPC or the explorer; a partial answer waits for the next round. The offer list reads every offer id and current offer state, skips cancelled or empty offers, and leaves maturity, APR and amounts for the contract to enforce; the auction list reads every open loan before filtering. A wallet's offers and positions named by the explorer are shown only after the contract names that wallet as maker or borrower. Writes go only to addresses from an address book keyed by chain ID, after checking the wallet's chain. It asks for `approve(tokenId)` on veBTC and exact amounts for MUSD and BTC, and never for `setApprovalForAll` on veBTC or on units. On-chain strings render as plain text. A retry sends only what the screen shows: changing any input clears a failed run. For each maturity it shows how many loans are open; each loan's own page shows its health. It sets `maxPay`, and the MUSD allowance for a purchase, at the price plus 1%, because the price can rise within a block (C11), starts a purchase over when the price rises above that cap, and never offers a purchase the contract must refuse (a safe LTV auction). The development test wallet is imported only when `NODE_ENV` is `development`, and a production build is checked for it before deploy.
- <a id="c22"></a>**C22.** A deploy fails unless all of these hold on that chain: every external address has code; `locked()` on a known tokenId decodes as C6 expects and its end is a multiple of 604,800; PriceFeed returns a fresh 18-decimal price; `CreditMarkets` and `LoanManager` each point at the other (C27); and the PassThrough library's runtime code hash equals the compiled artifact's, recorded in the deployment file.

### Credit-market specifics
- <a id="c23"></a>**C23.** No outside code runs inside post, cancel, fill, borrow, roll, repay, auction start, purchase, settle or finalise, apart from the fixed Mezo contracts and the reward contracts in C10. Units from a fill are recorded to the maker in storage and minted when the maker calls, so a reverting or hostile maker cannot fail a borrow that lists its offer. Each contract has one reentrancy lock over every state-changing function, and neither contract calls untrusted code while the other is mid-update.
- <a id="c24"></a>**C24.** One clock everywhere, with WEEK = 604,800 seconds. A maturity is valid only if it is a multiple of WEEK, which is exactly Thursday 00:00 UTC and the same rounding veBTC uses for lock ends. A maturity m is open for offers and new borrows while now < m. A loan at m can be repaid or rolled without default while now <= m. It is overdue when now > m, and its market can become final only when now > m. The vote cutoff is lockEnd - WEEK. The keeper and UI read all of these from contract views.
- <a id="c25"></a>**C25.** The treasury's fee is units at the same maturity, minted at fill beside the maker's. Units therefore equal debt and the treasury shares any shortfall pro rata with lenders. What can remain in a market is rounding dust from redemption and the share of units nobody claims or redeems; `CreditMarkets` never rescues MUSD or BTC, so that remainder stays put by design.
- <a id="c26"></a>**C26.** Every loan reaches Closed within a published time after its maturity: the auction duration, plus one epoch for a reset, plus the longest lock the position can then carry (the live `maxLockTime` after `increaseUnlockTime` or `unlockPermanent`). Settle needs no buyer and no DEX, so only an oracle outage can extend it (a stated non-goal). C26 bounds the time a date stays open. Since the review, lenders do not wait for it: from the date, `withdrawCollected` (C15) pays each holder's share of what has been collected, so an unpaid loan delays only its own share, which it can hold for the whole limit, about 5 weeks on a permanent lock and about 4.4 weeks on a normal lock extended to the maximum just before maturity (see the non-goals). Purchase and settle also decode `locked()`, so a veBTC change to its return size would stop every ending except repay and write-off; that is a Mezo upgrade, a stated non-goal. Test: a permanent lock voted in the trigger epoch with no buyer still leaves its market final within the limit.
- <a id="c27"></a>**C27.** `CreditMarkets` accepts fills and market credits only from the `LoanManager` address fixed in its constructor (precomputed from the deployer's nonce, or both contracts created by one factory in one transaction). `LoanManager` talks only to the `CreditMarkets` fixed in its own constructor. There is no setter and no initialiser that the first caller can use.
- <a id="c28"></a>**C28.** `LoanManager`'s MUSD and BTC balances are always at least the sum of recorded claimables. Each claimable is credited once and paid once, only to its recorded owner, and no settle or reward forwarding touches it.
- <a id="c29"></a>**C29.** No purchase pays the market less than min(D, value at the time of sale): every purchase pays at least the floor recomputed at a fresh price, max(floor x value now, min(D, value now)), and never less than the curve from the start value. A loan whose collateral covers its debt when it sells therefore never leaves a shortfall through an auction, a borrower can never buy their own position back below the debt while it covers the debt, and a rebound after the start raises the price for the borrower's benefit. A loan whose collateral does not cover it goes to settle. Tests: the audit's `AuctionNeverReanchors` tests and the fuzz test in `AuditFixes.t.sol`.

### General standards
1. **Primitives over lists.** A valid maturity is one predicate (`t % 604800 == 0`, within range), not a calendar table; it covers every Thursday 00:00 UTC and nothing else, and it does not cover timestamp drift by block producers. Collateral acceptance is one positive test (C2) that refuses any escrow type Mezo adds later; it does not cover a new transfer path an upgrade might add. Authorisation (C4) and pause (C19) each live in one shared path. Fill safety comes from never running maker code (C23), not from an allow-list of EOA makers, because `extcodesize` misses contracts under construction. Reward safety rests on three things together: the measured delta, the reentrancy lock, and no third-party inflow (C10); the last part depends on knowing every permissionless path that pays `LoanManager`, which is list-shaped: it covers the paths confirmed on fork and not one Mezo adds by upgrade.
2. **Normalize before compare.** One `locked()` decoder, one value, one price, one quote function for face and units, one clock (C24) and one BTC reader. Never add `address(this).balance` to `BTC.balanceOf`, because they count the same coins. The debt `LoanManager` records and the units `CreditMarkets` mints come out of the same quote call.
3. **Validate outputs like inputs.** Units are an output that others will price and trade, so mint only what C14 backs. Credits to a market are booked only against funds measured arriving (C14). Rewards and BTC from `withdraw` are measured deltas (C10, C12). Minted tokenIds are checked against `ownerOf` (C17). Events carry the normalised values the keeper and UI act on. The keeper treats RPC data as hints, and the UI renders strings as text.
4. **Fail closed.** Revert on an unknown `locked()` layout, a zero or stale price, a maturity that is not a week multiple, an offer for another maturity, a fill short of its listed amount, an `ownerOf` mismatch or an unknown state. Arrays are capped, keeper loops are bounded, and purchases carry `maxPay` and a deadline. Deliberate exception: exits and resolutions are never paused (C19), because blocking them pushes the loss onto whoever is stuck.
5. **Non-goals.** This system does not defend against:
   - A malicious or compromised Mezo contract or upgrade (veBTC, PoolsVoter, BoostVoter, fee distributor, MUSD, PriceFeed). A veBTC flaw reaches all collateral at once, as on 2026-10-05; the guardian can stop new borrows but cannot reverse a theft.
   - Wrong prices inside the 60-second oracle window, MUSD trading away from 1 USD, or an oracle outage longer than the C26 limit.
   - BTC price moves after a settle: lenders paid in BTC carry that price risk until they sell.
   - Losses shared across a maturity: every unit at that date shares any shortfall, including units held by lenders who never chose that loan.
   - Lenders who want out before maturity: units can be transferred, but the system provides no buyer and no price.
   - Interest after maturity: the face is fixed, and unit holders earn nothing while a late loan resolves.
   - Mempool griefing that only makes a borrow revert (a cancel or another fill landing ahead of it).
   - Keeper uptime: GitHub cron is best effort, and anyone can run the keeper.
   - The value of votes, bribes and boosts, none of which counts as collateral. Rewards a third party pays straight to `LoanManager` are not credited to anyone.
   - Mezo's PoolsVoter trusts an ERC-2771 forwarder. A flaw in that forwarder could act as `LoanManager` on PoolsVoter (vote, reset, claim) and bypass C4 and C5; rewards would still land with `LoanManager`, and the worst outcome is a delayed settle.
   - A secondary voter Mezo adds to veBTC after deployment: a vote there would block settle until Mezo's voter is reset by other means.
   - BTC that a stranger's fee distributor claim delivers for an expired held lock is credited to nobody, and the owner's `rescueToken` can move it, because it sits above the claimable totals. The owner is trusted to return it to that position's borrower.
   - A reward token (one a registered reward contract lists) whose own code calls out during a claim could, at most, move value that is credited to nobody into the measured window; it cannot reach claimables or another position's recorded funds.
   - A compromised user wallet or RPC, or an npm or Vercel supply-chain attack beyond lockfile pinning.
   - An owner key compromise beyond the C19 bounds.
   - A settings change inside the C19 bounds that lands just before a borrower's borrow or roll applies to that loan. The setters have no timelock; the UI shows the terms a loan will get (C21).
   - A delay, not a loss, on the share of a date still owed by an unpaid loan: it can wait until the C26 limit (about 5 weeks). Everything already collected can be withdrawn from the date (C15). A Claim cannot be sold; a market for units is planned for Wave 2.

# Wave 2 additions

Written on 2026-11-04 at the Wave 2 architecture gate, by the same method as Wave 1: a plain functional description of Wave 2 with security left out (a new version of LoanManager and CreditMarkets that parks idle offer MUSD in Mezo's sMUSD vault and lets a borrower name a reward operator, a new PayDown contract that turns rewards into repayment, and a new UnitMarket for credit units), then a separate review pass. Wave 1's sections still apply unless "Changes to Wave 1 rules" below says otherwise. The findings it raised are F26 to F35 in the table above.

## A) App-class risk profile (Wave 2)

Wave 2 keeps Doji's Wave 1 class and adds three more:
- An omnibus investor. CreditMarkets puts every parked maker's unfilled MUSD into one account at a vault that Mezo owns and can upgrade, then splits that account's yield among many makers with its own bookkeeping.
- Delegated authority plus a trade bot anyone can run. A borrower lets another address claim a position's rewards; PayDown sells those rewards on Mezo's pools and repays the loan with what comes back.
- An escrow market for transferable claim tokens. UnitMarket holds sellers' ERC-1155 credit units, swaps them for MUSD and takes a fee.

- **A14 Bookkeeping drift and over-crediting.** Doji works out each offer's yield from the vault's global index; the vault works out what it owes CreditMarkets from its own per-holder checkpoint. Two calculations of the same number, rounded differently at different times, drift apart. If Doji books more than the vault delivered, the gap would be paid from the balance that also holds every market's collected repayments and every unparked offer. A vault upgrade that makes the index jump would turn drift into a drain.
- **A15 Stale index across state changes.** An offer that keeps its old snapshot through a pull-out and a re-enable would book yield for weeks its MUSD earned nothing. Booking every offer at pull-out would loop over offers, which C13 forbids.
- **A16 Outside custody and shared liveness.** Post, fill, cancel and the fill half of a roll call the vault. A pause, fee, delay, short payment or revert in it would stop cancels and fills of parked offers and any roll that takes them. An unchecked short payment would be topped up from other users' MUSD, a bank run inside one balance.
- **A17 Approval scope and admin reach.** A standing MUSD approval to an upgradeable vault would expose every market's collected MUSD to its next upgrade. Wave 1's rescue rule protects MUSD and BTC; sMUSD now stands for every parked dollar.
- **A18 Caller-chosen price and route.** A harvest's route and minimum come from its caller, and the keeper's minimums come from pool quotes an attacker can move in the same block. A minimum of zero, or a quote from a moved pool, sells the borrower's rewards for almost nothing. Only BTC has an on-chain reference price (MUSD's PriceFeed).
- **A19 One shared balance across positions, and re-entry through the route.** PayDown is the operator for many positions and runs pool and token code the caller chose. If it repaid with its whole balance, or a hop could call harvest again mid-swap, one position's rewards could repay another's loan.
- **A20 Griefing and forced selling.** Anyone could call harvest with no swaps and switch off that week's pay-down, or call it on a position with little or no debt and force the borrower's BTC rewards into MUSD at a loss of up to the slippage allowance.
- **A21 What the operator can do, and stale delegation.** The operator is a new identity inside LoanManager's one borrower check (C4). It must reach claimRewards and nothing else, and must disappear with the position. LoanManager is close to its size limit, which creates pressure to trim checks.
- **A22 Fake assets and seller identity in an escrow market.** The old and new CreditMarkets both mint units with id = maturity, and anyone can deploy an ERC-1155 with the same ids. A market that accepts any arrival or keys listings by id alone could sell a fake or old-pair unit as a new one. Pulling units needs setApprovalForAll, which exposes every maturity a seller holds and which C21 forbids the UI to ask for.
- **A23 Rounding and partial fills in a priced trade.** A cost that rounds down lets a buyer take dust units for nothing; a buy that quietly fills less than asked is a different trade; a fee changed between listing and buy changes what the seller receives.
- **A24 Receiver hooks and stuck escrow.** ERC-1155 transfers call the receiver's hook; a hostile buyer can call back during a buy. A fee pushed to a treasury that refuses MUSD would block every buy. Units sent unasked must never become a listing.
- **A25 Off-chain: keeper budget and two deployments.** Weekly harvests share a small gas wallet with auctions and settles, so spam positions could starve resolution. The website and keeper read two contract pairs that share maturities and tokenIds; anything keyed by maturity alone acts on the wrong pair.

Still not applicable: SSRF; SQL, command or template injection; file upload; path traversal; sessions and cookies; database tenant isolation. Wave 2 adds no server and no database, and no permits or signatures (Quests add a server: see A26 and A36). Changed from Wave 1: "Doji never swaps on a DEX" becomes "Doji never sells collateral on a DEX; PayDown sells rewards, under C39". No Doji contract reads a pool price to value collateral, debt or units, and a listing price is never treated as a unit's worth (C47).

## B) Threat model (Wave 2)

**New trust boundaries**
- T9 The sMUSD vault: every number it returns (yieldIndex, supplyYieldIndex, claimableYield) and every MUSD or sMUSD amount it moves. Its code can change while its address stays the same, and it trusts an ERC-2771 forwarder to say who is calling (the pattern behind Mezo's 5 Oct veBTC incident); a flaw there would move every parked sMUSD at once, and every check in C30 to C35 assumes an honest vault.
- T10 Mezo's pool router, its factory, the pools, and every token on a route the caller names: their quotes, results and the code they run during a swap.
- T11 A position's reward operator: any address the borrower names. LoanManager sends it rewards and takes nothing it says as fact.
- T12 PayDown reading LoanManager: borrower, debt and loan state views, and the tokens claimRewards sends. LoanManager takes nothing from PayDown as fact.
- T13 UnitMarket reading CreditMarkets: units from the CreditMarkets fixed at deploy are real; every other ERC-1155 is untrusted.
- T14 Whoever calls harvest: gauges, tokens, swap list, routes, minimums, deadline and timing.
- T15 The old pair and the new pair: two sets of addresses with the same ids, neither taking the other's data as fact.
- T7 (transaction order) now covers harvest swaps and buys; T8 (RPC reads) now covers the keeper's router quotes and claimable-reward reads.

**Attacker-controlled inputs**
- Direct: when an offer is posted relative to the vault's yield lumps; the operator named in setRewardOperator; every harvest argument (tokenId, gauges, fee and bribe tokens, which tokens to swap, each route, minimum and deadline, duplicates); list and buy arguments; the timing of cancels and after-expiry returns; ERC-1155 arrivals at UnitMarket (contract, id, amount, operator, from, data, batches); tokens sent unasked to CreditMarkets, PayDown or UnitMarket; MUSD paid into the vault by anyone; new pools, trades, flash swaps and liquidity that move pool prices; incentives posted on gauges; receiver hooks on any party.
- Indirect: from the vault, the index (value, jumps, falls, overflow), claimable yield, checkpoints, the MUSD a withdraw or claim actually returns, the sMUSD a deposit actually mints, and any pause, fee or delay after an upgrade; from the DEX, quotes, outputs, reserves and hop-token behaviour; PriceFeed, now also a swap floor; the LoanManager views PayDown reads; stored values read back (offer snapshots and parked flags, parked principal totals, yield delivered and paid, operators, listings); events read by the keeper and UI, including look-alikes; owner settings and guardian timing.

**Privileged position and assets**
- CreditMarkets is the vault's one holder for every parked offer and receives all the yield; which maker gets which share is decided by Doji's bookkeeping alone. Its MUSD balance now mixes plain escrow, every market's collected MUSD, and yield delivered but not yet paid.
- LoanManager sends a position's rewards to whatever operator its borrower named.
- PayDown is the operator for every opted-in position; during a harvest it holds their rewards, approves the router, and can repay any loan.
- UnitMarket holds every listed unit and decides who receives each one.
- The guardian can move all parked principal between the vault and CreditMarkets; the owner can turn parking back on and set the unit fee and PayDown's slippage within caps. The keeper key holds only gas but now chooses routes.

**Attacker goals**
- G6 Take makers' money through the vault bookkeeping: yield booked above what the vault delivered (A14), a snapshot that survives a pull-out (A15), a short withdraw topped up from other balances (A16), an approval or rescue that reaches parked principal (A17).
- G7 Take borrowers' rewards: a sandwiched harvest (A18), a re-entered harvest or balance sweep that pays one position's rewards to another (A19), a forced sale on a position with no debt (A20).
- G8 Sell something fake or take units without paying: fake or old-pair units (A22), dust buys or a buyer hook calling back (A23, A24).
- G9 Redirect rewards or authority: an operator that survives onto a returning tokenId, or that can do more than claimRewards, or a phishing site that names the attacker as operator (A21).
- G10 Freeze money: a vault fault that stops parked cancels, fills and rolls (A16), harvest spam that starves resolution (A25), units stuck in UnitMarket (A24), a yield calculation that reverts and blocks principal with it.

## C) Defensive-programming standards (Wave 2, C30 onward)

### Parked offers (sMUSD)
- <a id="c30"></a>**C30.** Parked principal is exactly accounted for and never topped up from anyone else. CreditMarkets records total parked principal equal to the sum of parked offers' unfilled amounts, and its sMUSD balance is always at least that. A post parks only if the sMUSD balance rose by exactly the amount. A withdraw is accepted only if sMUSD fell by exactly the principal asked for and MUSD rose by at least that much; anything else reverts. A fill pays the borrower exactly the listed principal, from the withdraw in the same call, never from collected MUSD, plain escrow or yield. Test: a mock vault that returns 1 wei short makes fill and cancel revert, and no other balance changes.
- <a id="c31"></a>**C31.** Makers are paid yield only from yield the vault actually delivered. Each offer earns its principal times the index increase, rounded down, only while its principal was in the vault (C32). Total yield paid never exceeds the MUSD the vault delivered above principal, measured as it arrives. No yield payout takes CreditMarkets below the C14 solvency line. Yield booked to no one stays put and is credited to nobody. Makers are paid first come, first served from delivered minus paid, so if booked yield ever runs ahead of delivered (a few wei of rounding, I-01, or a vault that reports more than it pays) the last makers to withdraw are short, never lenders and never escrow. Yield never moves into a market or an offer's escrow, and escrow and collected funds never move into yield. Test: fuzz posts, fills, cancels, yield lumps and withdrawals with parked and plain offers; then set a mock index to 2^200 and show payouts stop at the yield delivered.
- <a id="c32"></a>**C32.** An offer is parked or plain from the moment it is posted, and its yield clock stops for good when its principal leaves the vault. The snapshot is taken after the deposit, in the same call. Stopping parking changes only later offers. Pull-out runs in fixed gas with no loop: it withdraws the recorded parked principal (never the raw sMUSD balance) and records the index once; every offer parked before it books yield only up to that index and stays plain afterwards. Re-enabling parks only later offers. The parking controls never change an offer's maker, amount, snapshot or booked yield. Test: post, lump, pull-out, lump, re-enable, lump, fill: the offer's yield is its share of the first lump only.
- <a id="c33"></a>**C33.** Fill and cancel book yield before moving money: yield on the remainder as it stood, snapshot moved forward, remainder cut, all before the vault is called, under the one reentrancy lock (C23).
- <a id="c34"></a>**C34.** No standing permission reaches parked money. CreditMarkets approves the vault for exactly the amount being deposited and leaves no allowance after the call. rescueToken never moves sMUSD. sMUSD sent unasked is credited to nobody and never counted as principal.
- <a id="c35"></a>**C35.** A vault fault stays inside parked principal. It can stop only posting while parking is on, fills and cancels of parked offers, pull-out, and yield withdrawal. It never stops fills or cancels of plain offers, repay, a roll that takes plain offers, redemption, withdrawCollected, finalize, or any resolution: none of those calls the vault or the router, and collected MUSD and BTC are never parked. A yield calculation never makes a principal movement revert for a vault that answers with well-formed data (a reply too short to decode fails the current era's parked fills and cancels, which a vault fault may stop anyway); an index that falls or is too large to multiply books zero for that period. Every keeper run simulates, from CreditMarkets' address, a vault withdraw of the total parked principal and fails loudly if it would not succeed.

### Reward operator (LoanManager)
- <a id="c36"></a>**C36.** The operator is one field of the position record. Only the recorded borrower can set or clear it. It is deleted with the record when the NFT leaves (C9), so a returning tokenId, or a position bought at auction and deposited by its buyer, has none. Naming the zero address clears it; naming LoanManager reverts. The operator passes the C4 check for claimRewards on that tokenId only, under the borrower's conditions (in custody, still owned by LoanManager; during an auction too, as C4 allows the claim). It can never call claimRebase, vote, reset, poke, extend, borrow, roll or withdraw.
- <a id="c37"></a>**C37.** Rewards go to whoever calls the claim: the borrower's claim pays the borrower, the operator's pays the operator, measured as in C10. Naming an operator never takes away the borrower's own claim, clear or repay. LoanManager relies on no PayDown code: the most a hostile or buggy operator can do is take the rewards of the positions that named it. The new LoanManager passes the full Wave 1 suite against C1 to C29 as amended here; no check is dropped or moved out to fit the size limit.

### PayDown
- <a id="c38"></a>**C38.** A harvest moves only what it received, inside one call that cannot be re-entered. PayDown measures its own balance change around claimRewards and each swap and uses only those amounts. Anything it holds outside a harvest is a stray credited to nobody and never swept. A token listed on both sides or for two gauges is measured once (a pool's fee and incentive contracts both pay MUSD and BTC); a token named twice in the borrower's swap list reverts. The borrower is read from LoanManager before any outside code runs, and everything not repaid goes to that address in the same call. Test: a route through a hostile token that calls harvest for the attacker's own position reverts, and MUSD donated to PayDown is untouched.
- <a id="c39"></a>**C39.** No harvest sells a reward below a floor the contract computes. For BTC, the MUSD received (PayDown's measured MUSD increase, never the router's return value) must be at least the BTC sold at the C7 price minus a slippage allowance the owner sets under a hard-coded cap; a caller's minimum can only raise that floor. A route must start at the token sold and end at MUSD. A token with no on-chain reference price is sold only in a harvest the borrower calls; in any other harvest it goes to the borrower unsold (Ram, F26). The caller never decides whether a token with a floor is sold. A stale or zero price reverts the harvest (C7). Test: on a fork, a pool moved 5% by a sandwich makes the harvest revert, and a caller minimum of 0 changes nothing.
- <a id="c40"></a>**C40.** A harvest sells only what the debt needs. With no open loan it sells nothing and sends every token to the borrower. Otherwise it sells no more of a token than covers, at that token's floor, the debt still owed after the MUSD already received in this harvest (in a permissionless harvest the caller decides which tokens are claimed, so BTC may be sold that MUSD rewards claimed later would have covered; the cost is bounded by the slippage allowance, A20), and a token the borrower names in harvestAndSwap is sold whole at the borrower's own minimum; it repays the smaller of the MUSD received and the debt owed, read just before the repay. MUSD over the debt goes to the borrower. Approvals to the router and LoanManager are exact and reset to zero.
- <a id="c41"></a>**C41.** A harvest changes a loan only by repaying it, runs only when the operator's claimRewards may run (also during an auction, so a harvest that covers the debt cures it), and reverts whole if any step fails, leaving the rewards in Mezo's reward contracts.
- <a id="c42"></a>**C42.** PayDown's addresses (LoanManager, router, PriceFeed, MUSD, BTC) are fixed in its constructor (C27). The owner can only set the slippage allowance under its cap, name the guardian, unpause, and rescue tokens PayDown holds outside a harvest (strays), which is safe only because PayDown keeps no balance between calls and the rescue cannot run inside a harvest; a change that leaves a balance behind must revisit the rescue; the guardian can only pause harvest. A paused PayDown never affects the borrower's own claim, clear or repay.

### UnitMarket
- <a id="c43"></a>**C43.** A listing exists only for real units of the CreditMarkets fixed in UnitMarket's constructor, held by UnitMarket. Arrivals from any other contract, batch arrivals, and arrivals that are not creating a listing revert. A listing is created by the holder's own transfer into UnitMarket with the terms in the transfer data, so no setApprovalForAll is ever needed (C21). The seller is the transfer's from, never the operator or the data. The units contract is part of a listing's identity. For every id, UnitMarket's unit balance equals the sum of open listings' units left.
- <a id="c44"></a>**C44.** A listing's seller, units contract, maturity, price, expiry and fee rate never change after posting, and listing ids are never reused. The fee rate is snapshotted at listing, under a hard-coded cap.
- <a id="c45"></a>**C45.** A buy is exact and paid in full: it fills exactly the units asked for or reverts, before expiry, at a price no higher than maxPricePerUnit, pulling the cost only from the caller. The cost is units times price rounded up and above zero; the fee is the cost times the rate rounded down; seller's amount plus fee equals the cost. The listing is updated before any token moves, units go only to the caller, under one reentrancy lock. Test: fuzzed dust buys never get units for 0 MUSD, and a buyer hook that calls back cannot buy more than the units left.
- <a id="c46"></a>**C46.** Exits from UnitMarket are never blocked: the seller can cancel at any time, and after expiry anyone can return the units to the seller, whatever the pause, fee or market state. The fee is credited to the treasury as a claimable (as F24; `setTreasury` hands fees already owed to the new treasury), MUSD sent to UnitMarket by mistake can be rescued only above the fees owed (I-04), proceeds go only to the seller, and rescueToken never moves units held for open listings or MUSD owed to anyone. Non-goal: a seller contract whose own receiver hook refuses units cannot cancel, and its expired listing cannot be returned to it.
- <a id="c47"></a>**C47.** Listing prices are seller input and never a value: no contract, keeper decision, or UI health or value figure uses a listing or trade price as the worth of a unit or of collateral. A unit is shown at 1 MUSD only before its maturity; once the date has passed the UI shows no yield on a listing and points to what the chain says the unit redeems for (added 4 Nov after the section 13 review). Each buy step checks the date again when it is sent. Known limit: the website judges the date on the device clock, and UnitMarket checks only the listing's expiry, so a buy signed just before a Thursday and mined after it buys a dated unit; the website's own listings expire the day before the Thursday.

### Off-chain, and the two pairs
- <a id="c48"></a>**C48.** The keeper's harvest job treats router quotes and RPC reads as hints; the contract floors (C39) protect the borrower. Every resolution job for both pairs runs before any harvest. Harvests come out of a separate capped budget (positions per run, tokens per harvest, route length, gas), read each position's current operator and claimable rewards from the chain, skip positions whose rewards are worth less than the harvest costs, simulate before sending, and say so when a run skips harvests. The worth-it floor is a fixed 0.01 MUSD, which is safe at testnet gas prices only; a mainnet keeper re-derives it each run as at least estimated gas times gas price times the oracle price. Known limit: harvest candidates come from RewardOperatorSet logs (explorer, then the node's recent window), so while the explorer is down a position named long ago is missed until it returns. Claim plans cover the pools a position votes for now; rewards still waiting on pools it voted for in an earlier week are claimable through LoanManager but are not offered by the keeper or the site. PayDown reads the price whenever BTC arrives for an open loan and sells under the C39 floor in one transaction, so an unavailable oracle, or a pool paying below the floor (seen live on 5 Nov: 1.44% under the oracle against a 1% floor), refuses a harvest that brings BTC, even when its MUSD alone covers the debt. The keeper and the website then retry the same harvest with BTC left out of the claim: the MUSD repays, and the BTC stays in Mezo's reward contract for a later harvest.
- <a id="c49"></a>**C49.** Two pairs, one key. In the keeper and the UI every offer, loan, unit balance, market, listing and harvest is identified by chain id, contract address and id, never by maturity or tokenId alone; old and new units at the same maturity are different assets. A write goes to the contract that holds the object it acts on, and no new-pair contract takes the old pair's data as fact.
- <a id="c50"></a>**C50.** The UI shows an offer's yield as what withdrawOfferYield would pay, from a contract view, and whether its MUSD is still in the vault from `isInVault` (I-02). Harvest history and listings come only from events of address-book contracts, re-read by id before being shown or acted on. The pay-down switch only ever names the address-book PayDown, and a position whose operator is anything else shows a warning. A buy asks for an exact MUSD allowance computed with the C45 rounding. The operator warning, with a way to remove the operator, shows on every screen that shows a Wave 2 position, in every loan state, including a position held with no loan. "Earned in sMUSD" is yield booked to the lender; withdrawOfferYield pays it as the vault delivers, so the UI says a withdrawal can pay part now and the rest later. On the Wave 2 pair the borrower's own claimRewards is offered during an auction (C41, audit L-01). As a rule rather than a list of screens: any view that renders a Wave 2 position whose operator is neither zero nor PayDown renders the warning, whatever network the wallet is on.
- <a id="c51"></a>**C51.** Deploy checks extend C22: the vault has code and a fork dry run shows deposit minting 1:1 and withdraw returning at least the principal to CreditMarkets' address; the router and factory have code; PayDown's fixed addresses are the new LoanManager, the router, PriceFeed, MUSD and BTC; UnitMarket's CreditMarkets is the new one; the slippage allowance and unit fee are within their caps; the address book keeps the old pair's addresses unchanged.
- <a id="c52"></a>**C52.** Rolls and borrows during a vault outage. When the keeper's vault simulation (C35) fails, the website builds borrows and rolls from plain offers only and warns any borrower whose loan matures within two weeks that parked offers are unavailable; the guardian's pull-out (C32) turns every parked offer plain, but only when the vault pays the whole parked principal back; if `pullOut` reverts (a vault with limited liquidity or a fee, I-03), the guardian stops parking and lenders cancel parked offers one by one, each as far as the vault pays. Non-goal: during an outage a roll can lack liquidity if too few plain offers exist. Non-goal: the outage check simulates withdrawing the whole parked principal at once, so a vault with limited liquidity drops every parked offer from borrows and rolls even when a small fill would pass.
- <a id="c53"></a>**C53.** No write sends a bound looser than the one on screen. Where the app re-reads a quote, a minimum or a price at click time (a reward sale's minimum, a buy's maximum price, a roll's quote), it sends the tighter of the fresh value and the one the user saw, and a contract refusal is shown as a refusal. This generalises C21's retry rule.

- C3: CreditMarkets gains one call target, the vault, fixed at deploy, with no allowance outliving a call (C34). LoanManager gains no call target: the operator only receives transfers.
- C4: the shared check returns "borrower" or "operator", and only claimRewards accepts the operator (C36).
- C9: the position record also holds the operator and deletes it with the record.
- C10: "pays the borrower" becomes "pays the caller: the borrower, or the position's operator" (C37).
- C13: the ban on loops over offers covers pull-out (C32); listings and opted-in positions are found off-chain.
- C14: the solvency line becomes: MUSD held is at least the plain offers' unfilled amounts, plus each market's collected MUSD minus paid out, plus yield delivered minus yield paid; and sMUSD held is at least the parked offers' unfilled amounts. Yield is a third kind of payout, paid only by withdrawOfferYield (C31).
- C15: units held by UnitMarket cannot be moved into a Claim or redeemed until returned or bought; a sold unit carries its whole entitlement.
- C16: a cancel of a parked offer can be blocked by the vault (C35, F27). "A fill cuts the remainder before any other step" becomes "book, then cut, both before any outside call" (C33).
- C17: "pulled only from the caller" covers buy and list; PayDown repays from its own measured balance; every approval is exact.
- C18: stray sMUSD, and anything sent unasked to PayDown or UnitMarket, is credited to nobody.
- C19: the guardian gains stop-parking and pull-out; the owner gains re-enabling parking, the unit fee and the slippage allowance, each under a cap. Never paused now also covers withdrawOfferYield, UnitMarket cancel and return, and the borrower's own claim and operator clear. CreditMarkets' rescue never moves MUSD, BTC or sMUSD. The response to a Mezo change covers the vault and router: stop parking, pull out, pause harvest.
- C20: the keeper's role check covers all six contracts, and it gains the harvest job under C48.

- C25: CreditMarkets never rescues MUSD, BTC or sMUSD, and rounding dust from yield stays put.
- C27: PayDown fixes the new LoanManager and UnitMarket the new CreditMarkets in their constructors; the new pair fixes each other and never points at the old pair.
- Untouched: C1, C2, C5 to C8, C11, C12, C24, C26, C28, C29. Fills of parked offers still meet C8 exactly. Resolutions never call the vault or the router, so the C26 time limit does not change.

### General standards (Wave 2)
1. **Primitives over lists.** Swap safety is one floor from one price (C39), not a list of approved pools or routes; it does not cover tokens with no reference price, moves inside the slippage allowance, or the 60-second oracle window. Yield safety is one line: paid never exceeds delivered and never goes below solvency (C31); "delivered" counts only the vault calls CreditMarkets makes itself, so MUSD arriving any other way is credited to nobody and a miss leaves makers short, never lenders. Unit identity is one check, the sender is the fixed CreditMarkets (C43). The operator's scope is one branch of the C4 check. Vault health is one simulation per keeper run (C35).
2. **Normalize before you compare.** Doji's per-offer yield and the vault's per-holder yield are the same number from two calculators, so C31 caps payouts at what was delivered. PayDown values BTC with the C7 price code and never adds the native balance to BTC.balanceOf. Units are keyed as contract plus id everywhere. The UI computes a buy's cost with the C45 rounding.
3. **Validate outputs like inputs.** Keeper minimums are hints (C39). Router and vault return values are never used; measured balance changes are (C30, C38). Listing prices are never a value (C47). The UI re-reads state by id before acting on an event.
4. **Fail closed.** Revert on a short vault payment, sMUSD minted that differs from the amount, a swap below its floor, a stale price in a harvest, any ERC-1155 arrival that is not creating a listing, a buy for more than is left or at zero cost, and a token named twice in a borrower's swap list (claim lists are deduplicated, C38). Caps on harvest arrays and route length, the keeper's harvest budget, and MAX_FILLS rechecked for gas now that a parked fill calls the vault. Deliberate exceptions: a broken yield calculation books zero instead of reverting, so principal can still move (C35); UnitMarket exits and yield withdrawals are never paused.
5. **Non-goals.** Wave 2 does not defend against: a failure, loss, pause, fee or upgrade in Mezo's sMUSD vault (while it refuses withdrawals, parked offers cannot be cancelled or filled, and a pull-out also needs it to work); deposits timed around the vault's yield lumps, which dilute every holder equally as the vault is designed; price moves and ordering profits inside the slippage allowance and the oracle window; reward tokens with no reference price, which are sold only when the borrower runs the harvest with their own minimum (F26); thin pools (a harvest that cannot meet its floor reverts and waits); a borrower who names a hostile operator (they lose that position's rewards, never its collateral or debt); a unit buyer's risks (UnitMarket gives no price, no buyer and no guarantee; a buyer takes on that maturity's shared losses); on testnet, yield timed inside one transaction (Mezo's testnet vault has no fee collector wired, so anyone can trigger a payment and take a capital-weighted share of it with a parked post and a cancel; mainnet's vault pulls pending fees before each deposit); a cap on the total parked in one vault (a mainnet launch decision, F27); a borrower who wants MUSD-only pay-down without BTC sales (naming no operator is the only switch today); the deploy giving one key every role, which is a testnet setup: before mainnet the owner becomes a multisig and the guardian a separate key (I-06); gaps in the old pair, which keeps Wave 1's rules.

### To confirm on a fork before C30 to C35 are final
Whether an sMUSD deposit pays out accrued yield; whether anyone can send yield to CreditMarkets other than through its own calls; whether sMUSD is transferable and whether yieldIndex can fall; whether deposit or withdraw can be paused, capped or delayed; whether a router route names a factory the caller chooses; whether Mezo's pools allow flash swaps; which tokens the testnet gauges pay; whether the old pair is paused for new offers and borrows once the new pair is live.

## A) App-class risk profile (Quests)

Quests keep Doji's earlier classes and add four more:
- A public spender. An endpoint anyone can call signs and pays for a transaction with a private key held on a server (a hot key), for a recipient the caller chose. One bot check stands between the internet and that key.
- A scoreboard built from public data. EXP and rank come from logs read through third-party APIs, about actions anyone can repeat with as many wallets as they like.
- A renderer and fetcher driven by a URL. A public page and a PNG take any address from the path, query upstream services with it, and publish the result under Doji's name.
- A session bridge to phone wallets through a third-party relay, on the same origin as the pages above.

- **A26 Confused deputy with a hot key.** `POST /api/faucet` turns an anonymous request into a transaction signed by the relayer. The caller picks `to`, and Doji supplies the key, the gas and the faucet's balance. If the route can be made to sign anything other than one `claim` on one contract on one chain, the attacker spends with Doji's authority. The nonce and gas price come from a public RPC, so a bad answer there also shapes what gets signed.
- **A27 One bot gate.** Turnstile is the only check before the key. It fails if the reply is read loosely, if a siteverify outage is treated as a pass, if a token solved on another site is accepted (the sitekey is public), if a local-testing bypass reaches production, or if Cloudflare's published always-pass test secret ends up in production. The caller's IP is read from a request header, so the wrong header lets the caller choose it.
- **A28 Check then act, with no memory.** With no database, each serverless call sees only the chain. Parallel calls for one address, or for the last slot of the day, all pass `claimed` and `claimsOpen` before any lands. The contract refuses the extras, but the relayer has paid gas. Two calls can also take one nonce, leaving the browser watching a hash that never lands. One stuck low-priced transaction stops every later one.
- **A29 Pre-checks that miss a failure.** The route reads two views. A paused faucet, a faucet short of BTC or MUSD, and a recipient that refuses payment all pass those reads and revert on chain at the relayer's cost. A revert leaves `claimed` false, so the same address can fail again and again.
- **A30 Outside code inside a claim.** `claim` sends native BTC to an address the caller chose, which may be a contract. Its receive code runs mid-claim and can revert, burn all the gas it is given, or return a huge blob. It cannot re-enter `claim`, because only the relayer may call it.
- **A31 Faucet accounting and admin.** A kit could pay one token and not the other. If the owner lowers the limit below today's count, a plain subtraction in `claimsOpen()` underflows, the view reverts, and the route stops. BTC shows up two ways (native and ERC-20), so a balance or withdraw can count the same coins twice. Setters with no ceiling let one typo empty the faucet in a day.
- **A32 Keys in a shared codebase.** The relayer key and Turnstile secret are environment variables. The ways out: a public-prefixed name, a module pulled into the browser bundle through the quest library (which the browser and the server routes must both use), a preview build of a public repo, error text or logs, and one key doubling as owner, keeper or seed wallet.
- **A33 Scores from logs anyone can imitate.** Any contract can emit an event with the same signature as Doji's, and the old and new pairs share signatures. Attribution is the deeper trap: every claim's transaction sender is the relayer, a repay or harvest can be sent by someone other than the borrower, and a view shows today, not history.
- **A34 Two calculators, two spellings.** EXP is computed in the browser for one wallet, on the server for all wallets, and on the server again for the image. The explorer and the RPC shape logs differently (decoded fields against raw topics, checksummed against lowercase addresses). The bonus file and the exclusion list are typed by hand. A casing mismatch fails silently: an excluded wallet stays on the board, a bonus goes nowhere, and maker-differs-from-borrower passes for one wallet.
- **A35 Farming and paid-for behaviour.** "Doji may use it in future" invites farming, and the faucet supplies the capital. "A different wallet" costs one person two wallets. EXP also pays people for permissionless actions whose cost lands on others: a harvest on a stranger's loan forces the sale cost A20 accepted when nobody gained from it.
- **A36 Upstream calls built from a URL.** The image route puts an address from the path into a server-side explorer query. A hostile string could reshape that request. Hosts are fixed, so SSRF (making a server fetch somewhere it should not) is narrow, but it now applies: a redirect, a next-page value echoed from a reply, or string-built URLs would reach it.
- **A37 Unbounded work on public routes.** There are 2^160 valid addresses, and a loose parser accepts thousands of casings of each, every one a fresh render and fresh upstream calls. The leaderboard rescans all events on each cache miss, and a query string may create a new cache entry. Faucet-funded spam makes the scan longer. The costs land on the hosting quota and the shared explorer rate limit. If either runs out, the site or every quest read goes down.
- **A38 Partial data that looks final.** Explorer lag, a page cap or a timeout gives a lower EXP and a wrong rank. It is then cached for 60 seconds, and X keeps a card it has fetched for far longer. An empty reply during an outage looks like 0 EXP.
- **A39 Content published under Doji's name.** If raw URL text reached the image or metadata, anyone could mint a Doji-branded picture with their own words. A bonus `link` of `javascript:` would run on the origin that holds wallet sessions. Explorer hashes become links.
- **A40 A URL address that drives an action.** `/quests/<address>` shows any wallet. If a claim button used the page's address, a shared link would make every visitor solve a Turnstile for the attacker's wallet.
- **A41 A hand-edited file in a public repo.** `bonus-exp.json` adds directly to EXP. A string `exp` concatenates in JavaScript ("100" plus 50 gives "10050"), a bad entry breaks every total, a duplicate in another casing double counts, and anyone can open a pull request against it. Its `reason` and `link` began as a reporter's text, and git history keeps the wallet-to-identity link for good.
- **A42 Phone wallet sessions and third-party code.** A public project ID can be reused by a look-alike site unless it is tied to Doji's origins. A session's account and chain can differ from what the page assumes. The session lives in browser storage, so any script flaw on this origin can ask the wallet to sign. The connector adds a large dependency tree, and Turnstile's script runs on the same origin.
- **A43 Doji's own seed wallets.** They act in the same shared markets as testers. C15 shares what a date collects across every unit there, so a seed loan left unpaid on purpose delays testers' money at that date. Seed wallets would top the board unless excluded, the list can lag, and a seed key can drift into another role.
- **A44 Old limits meet new traffic.** The faucet hands out capital and the quest list sends people through every flow. C20's per-run bounds (150 open loans, 32 dates), C21's full reads of offers and open loans, and C48's harvest budget were set for a handful of users.

Not applicable: SQL and command injection (no database, no shell); file upload; path traversal (seal art is chosen by a computed rank, never a URL value); sessions and cookies, so CSRF does not apply either (a cross-site POST is only another anonymous caller, and C60 governs it); tenant isolation (no per-user data is stored); re-entry into `claim` (only the relayer may call it). Claims carry no price, so ordering attacks reach only who gets the last slot of a day.

## B) Threat model (Quests)

**New trust boundaries**
- T16 Any internet caller into `POST /api/faucet`: body, headers, source address, timing, parallelism.
- T17 Cloudflare's siteverify reply into the decision to sign.
- T18 Mezo's public RPC into the signer: nonce, gas price, simulation result, view results, returned hash.
- T19 The relayer's call into the Faucet: the caller is trusted, the `to` it carries is not.
- T20 The Faucet's BTC payment to `to`: outside code runs.
- T21 Explorer and RPC replies into the quest engine, the leaderboard and the image: logs, pagination values, status, redirects, timing.
- T22 The URL path into the page, its metadata, the image and upstream queries.
- T23 The bonus file and pull requests into the build and EXP.
- T24 Reown's relay and the phone wallet into the page: session, account, chain.
- T25 Vercel (variable scopes, CDN cache, logs, the headers it sets), plus third-party scripts on the same origin.
- T26 EXP into anything that reads it later. A future reward would be a consumer of today's numbers.
- T27 Doji's seed wallets into shared markets. Doji's own actions are inputs to testers' outcomes.
- T8 (public RPC) now also feeds a signing server.

**Attacker-controlled inputs**
- Direct: `address` in any type, length or casing; `turnstileToken`; raw body, method, content type; request rate and parallelism; timing around 00:00 UTC; forwarded-address headers, Host, cookies, query strings; the path address; the code at `to`, including code that behaves differently in simulation and on landing; how many wallets they make; every on-chain quest action, dust included; look-alike contracts and events; pull requests against the bonus file; a reporter's text and link; links shared on X.
- Indirect: siteverify's reply (success, hostname, action, errors, timing); RPC answers (nonce, gas price, simulation, views, hash, chain id, lag); explorer replies (logs, decoded fields, casing, timestamps, pagination, status, redirects, size, lag); the faucet's balances, which anyone can run down; the relayer's balance; stored values read back (`claimed`, the day's count, the bonus file, cached leaderboard JSON, CDN entries, X's cached card, the session in browser storage); the account and chain a wallet reports; owner settings.

**Privileged position and assets**
- The relayer key is the only way to call `claim`. It can dispense up to the day's limit and spends its own gas.
- The Faucet holds all kit funding, and the owner can withdraw it.
- The Turnstile secret, plus the routes' outbound network, explorer rate allowance and hosting quota, are all shared with the rest of the site.
- Doji's domain: anything running on this origin can ask a connected wallet to sign, and anything published here carries Doji's name.
- The leaderboard and rank are Doji's public statement of who earned what. The bonus file is Doji's discretionary score.
- Seed wallets hold the liquidity testers see.

**Attacker goals**
- G11 Shut testers out by emptying the day's claims, the faucet or the relayer's gas: fresh wallets at 00:00 UTC, hostile recipients, parallel requests, a paused or empty faucet, a high gas price, a stuck nonce (A27 to A31).
- G12 Get the relayer key or Turnstile secret, or make the route sign something else (A26, A32).
- G13 Hold a rank without earning it: look-alike events, wrong attribution, a casing escape from the exclusion list, a bonus entry, Sybil farming (A33 to A35, A41).
- G14 Take the site down or burn its quota: address and query-string floods, cache busting, event spam, an explorer ban (A36 to A38).
- G15 Turn Doji's domain on its visitors: a share link that spends their Turnstile for an attacker, branded fake images, script on the origin driving a wallet session, a look-alike site using Doji's project ID (A39, A40, A42).

## C) Defensive-programming standards (Quests, C54 onward)

### Faucet contract
- <a id="c54"></a>**C54.** A claim is one whole kit, to one address, once ever. Only the relayer can call `claim`. `claimed[to]` and the day's count are written before any value moves. One transaction pays exactly the set BTC and the set MUSD to `to` and emits one event naming `to`, or it reverts whole and `claimed[to]` stays false. A `to` of zero or the faucet itself reverts. Test: a recipient that refuses BTC, a faucet short of either token, and a second claim for one address each leave balances and `claimed` unchanged.
- <a id="c55"></a>**C55.** Recipient code has a fixed price. The BTC payment forwards a fixed gas allowance, large enough for a smart-contract wallet's receive function and no larger, and never copies return data. There is no "is this a contract" check: it would block smart wallets and misses contracts not yet deployed. Test: recipients that loop forever, return 1 MB or call back into the faucet each cost at most the C59 gas limit and change nothing; a proxy wallet receives a full kit.
- <a id="c56"></a>**C56.** The faucet's views tell the truth and never revert. One function turns block time into the UTC day, for `claim` and for `claimsOpen()` alike. `claimsOpen()` returns 0 when today's count is at or above the limit, including after the owner lowers the limit mid-day, and also when paused or when the contract cannot pay one full kit. Test: lower the limit below today's count and the view returns 0.
- <a id="c57"></a>**C57.** No burst can take a whole day. Claims so far today never exceed what has been released so far, with the limit released evenly across the UTC day. A sweep at 00:00 takes only the first share, and keeping testers out means solving tokens all day. Test: fuzz claim times across a day and assert the count never passes the released amount.
- <a id="c58"></a>**C58.** The owner's reach is bounded and the faucet owes nobody. Setters keep the amounts and the daily limit under hard-coded caps. Pause stops `claim` only. Withdraw pays only the owner. BTC is read one way, because native BTC and the BTC ERC-20 are the same coins, and nothing adds them together. Plain BTC or MUSD sent in is funding, credited to nobody, and `claim` is not payable. Ownership moves in two steps and cannot be renounced.

### Claim endpoint
- <a id="c59"></a>**C59.** The route can sign one shape of transaction: `claim` of a parsed address, to the address-book faucet, on chain 31611, value zero, with gas limit and gas price at or under constants. Chain id, target and function are constants in code, never read from the request or an RPC answer. A gas price over the ceiling is a refusal. The server has no general send function. Test: a mock RPC reporting chain 31612 or 1,000 times the normal gas price gets nothing signed for chain 31612 and nothing above the ceiling.
- <a id="c60"></a>**C60.** No verified token, no signature. Every path to the signer passes one check: Cloudflare's reply parses, `success` is exactly true, the hostname is Doji's production host, and the action is the faucet's. A missing secret, network error, timeout, non-200 or malformed reply is a refusal. No flag, header or environment name skips it. The token is a string of at most 2,048 characters sent through a form encoder, so it cannot add fields to the request. Test: each case above against a mock, plus a replayed token and a token from another hostname.
- <a id="c61"></a>**C61.** The IP sent to Cloudflare is only the value the platform sets, never one a caller can supply. If absent, the field is left out. Doji stores no IP and logs no IP or token.
- <a id="c62"></a>**C62.** Only a transaction that simulates gets sent. Before signing, the exact call is simulated from the relayer's address at the C59 gas limit. The `claimed` and `claimsOpen` reads choose the refusal message and never permit a send. A simulation that fails or cannot run is a refusal. A relayer balance under one claim's cost is a refusal: the caller reads `faucet_empty`, and the log says the relayer is short. Test: paused, no BTC, no MUSD, day full, already claimed and a hostile recipient each leave the relayer's nonce and balance unchanged. Not covered: state that changes between simulation and landing, which C55 and C63 bound.
- <a id="c63"></a>**C63.** Wasted relayer gas is bounded without a database. The relayer has at most a small fixed number of transactions in flight, read from the chain, and above that the caller is told to try again shortly. Two calls that pick one nonce collide, and the loser gets a refusal, never a hash. The hash returned is computed from the signed bytes, never taken from the RPC's answer. A transaction stuck at the head of the queue is replaced at the same nonce within the C59 ceiling, so one stuck nonce cannot stop claims for good. Test: 20 parallel POSTs with 20 valid tokens for one address land one claim and at most the in-flight number of failed transactions.
- <a id="c64"></a>**C64.** Input is checked cheap-first and output is a closed set. POST only, body at most 4 KB, a JSON object whose `address` and `turnstileToken` are strings. The order is format, Turnstile, chain reads, simulation, signature, so an unverified caller never reaches the RPC or the key. Every outside call has a timeout, and the route has a total budget under the platform limit. The reply is a hash or one code from a closed list, never upstream error text, a stack, an RPC URL or a variable name. The browser shows success only when a receipt for that hash from the faucet address names the wallet, or `claimed(wallet)` reads true; after a fixed wait it says it could not confirm and re-reads `claimed`.
- <a id="c65"></a>**C65.** Keys stay in one place and do one job. The relayer key and Turnstile secret are set for Vercel's Production scope only, so previews and fork builds have neither and their route refuses. Neither has a public-prefixed name. The module that reads them is server-only, and a build fails if browser code reaches it, directly or through the shared quest library. A production bundle is checked for both before deploy (as C21 does for the test wallet). A deploy check refuses if the relayer matches the owner, pending owner, guardian, treasury, keeper or any seed wallet. A stolen relayer key reaches one day's claims and its own small gas balance, until the owner replaces it.

### Quest engine
- <a id="c66"></a>**C66.** One address parser. Every address (request body, URL, explorer, RPC, bonus file, Doji's wallet list, quest table) goes through one strict parser into one canonical form before any compare, map key, cache key or display. Wrong length, a bad mixed-case checksum and non-strings are refused. Nothing compares raw address strings. Test: one wallet spelled in lowercase, uppercase and checksum form across every source gives one row and one total.
- <a id="c67"></a>**C67.** Only Doji's contracts can earn EXP. A log counts only if its emitter is a quest-table contract from the address book for chain 31611 (C49), its first topic is that row's event, it is at or after the deploy block, and it is not marked removed. Logs are decoded from raw topics and data by one ABI decoder, whichever source supplied them. Explorer decoded fields and labels are never read. Test: a look-alike contract with the same event signature and an old-pair log both earn 0 EXP.
- <a id="c68"></a>**C68.** One quest table. Each quest is one row: contract, event, the event field that names the wallet, any extra condition. That field decides the wallet, never the transaction's sender, because the relayer sends every claim. An event not in the table earns nothing. A quest is decided from logs alone, so it stays earned after a record is deleted (C9); views may add display detail and never decide a quest. Conditions: "a different wallet" needs maker and borrower to differ after C66; "buy units" needs buyer and seller to differ; "name PayDown" needs the operator to equal the address-book PayDown; a harvest counts only if it repaid more than zero (F45); "after a date" rests on the contract's own rule (C15) and no browser clock. The date shown is the block's timestamp.
- <a id="c69"></a>**C69.** One EXP function. EXP is one function of normalised logs and the bonus file, in one module used by the browser, the leaderboard and the image, so all three agree on the same logs. EXP is an integer. Each quest counts once per wallet however many logs match. Rank depends on EXP alone. Ties in the top 50 break by a fixed rule: earliest block reaching that EXP, then address. Changing a quest's EXP is a public commit, and anyone can rebuild a wallet's EXP from the repo and the chain. Test: one set of fixture logs through the browser and server builds gives identical totals and ranks.
- <a id="c70"></a>**C70.** An incomplete read is never shown as a final number. A timeout, error, page cap or reply that fails C67 marks the whole read incomplete. The page says so. The leaderboard serves its last complete result with its age, or says it is unavailable. The image uses a card with no number. An incomplete result is never cached as complete. Blocks the explorer has not indexed yet are read from the RPC within a fixed bound (as C20 does). Test: a mock explorer that fails on page 3 produces no final EXP.
- <a id="c71"></a>**C71.** EXP decides nothing today. No contract, keeper step, faucet limit, gate or payout reads EXP, rank or the leaderboard, so a wrong EXP cannot move money. Any future use needs a new threat model pass, a snapshot read directly from the chain, and its own Sybil rules. Every page and image showing EXP says no more than the published sentence: no amount, date or token is implied.
- <a id="c72"></a>**C72.** Outbound calls have a fixed shape. Only a C66 address reaches an upstream URL, through a URL builder. Hosts are constants and redirects are refused. Replies have size and time caps. A pagination value from a reply is checked as a cursor, never used as a URL, and each page counts against a fixed page cap. Test: a redirect to another host, or a next-page value that is a URL, ends the read as incomplete.

### Leaderboard and bonus file
- <a id="c73"></a>**C73.** Public routes do fixed work. No volume or variety of requests to `/api/leaderboard`, a quest page or the image raises upstream calls above a fixed rate. The cache key ignores query strings, headers and cookies, and each response depends only on chain data and the bonus file. An address has one URL spelling: other valid spellings redirect to it by relative path, never using the Host header, and anything else is a 404. The server keeps one cached snapshot of every wallet's EXP, and the image reads that snapshot instead of scanning per URL; the API returns 50 rows, and a wallet with no EXP gets one static card. Test: 500 requests with distinct query strings and address spellings produce at most the fixed number of scans.
- <a id="c74"></a>**C74.** A bad bonus file fails the build and is never partly applied. Each entry's address passes C66, `exp` is a positive integer under a hard-coded cap, `reason` is plain text under a length cap, `link` parses as https, and one wallet appears once after normalising. `reason` renders as text. An entry is added only with the reporter's yes, because git history keeps the wallet-to-identity link for good (F46). Test: `exp: "100"`, `1e309`, `-5`, `link: "javascript:alert(1)"` and a duplicate in another casing each fail the build.
- <a id="c75"></a>**C75.** Doji's wallets are one list, and it cannot lag. Deployer, owner, guardian, treasury, keeper, relayer and every seed wallet sit in one address-book list. The seed script refuses to sign with a wallet not on it. The leaderboard removes listed wallets after C66. This is a display filter: those wallets keep their public pages, which say they are Doji's. It covers Doji's own keys and does not cover a friend's or an insider's wallet. Test: a listed wallet in mixed case with the top EXP does not appear; a seed run with an unlisted key refuses.

### Share page and image
- <a id="c76"></a>**C76.** An address from a URL is only ever displayed. It never becomes a claim recipient, a transaction target, a spender or a signature field. Every button on a quest page acts for the connected wallet alone. A page for another wallet says so, shows the full address, and offers nothing in that wallet's name. Test: connected as A on B's page, a claim carries A or is not offered.
- <a id="c77"></a>**C77.** The image and metadata carry only values this code computed. Everything rendered comes from the parsed address, the rank and the EXP. Raw URL text never reaches the image, title, description, a log or an error. There is no `exp` or `rank` parameter. An invalid address is a 404 with no image. Seal art is bundled, a render fetches nothing remote, and a render has time and size ceilings. Absolute URLs in metadata come from a constant origin, never the Host header. Test: `/quests/<script>`, an encoded slash, a 10 KB path and `?exp=999999` each give a 404 or change nothing.
- <a id="c78"></a>**C78.** Upstream values are checked as input to the page. A transaction hash must be 32 bytes of hex before it enters a link, links use a constant explorer base, and leaderboard JSON is checked against a schema in the browser. External links carry no opener. Another site cannot frame quest pages. The only scripts on the origin are the app's bundle, Cloudflare's widget and what the wallet connector needs, because any script here can ask a connected wallet to sign. Cloudflare's widget loads only when a user reaches the claim step.

### Phone wallets
- <a id="c79"></a>**C79.** Phone wallets get the same rules as browser wallets. The project ID is public and not tied to Doji's origins (Reown's allow-list is left open), so a look-alike site could reuse it; that is a non-goal, because a wallet's own prompt shows the site asking. The app name and URL in session metadata are constants, and so are the `wallet_addEthereumChain` values. Before every write, the session's current account and chain are read and must match the screen and chain 31611 (C21); a wallet that cannot add or switch gets a plain message and no write. Connecting and claiming ask for no signature. An account change or disconnect clears the page's wallet state. The connector's packages are pinned in the lockfile and load only when the user picks them. Test: a phone wallet on chain 31612 cannot send a write.

### Seed wallets, load and deploy
- <a id="c80"></a>**C80.** Seed wallets are ordinary users. They hold no role and use no private path. A seed loan left to reach auction shares its date with every unit there, so the site says so before a tester lends at that date (F44). Seed loans carry collateral above their debt, so the effect stays a delay and not a shortfall (C29). Test: the warning shows on a date holding a seed loan.
- <a id="c81"></a>**C81.** Earlier limits are rechecked at quest volume. With the faucet funding its full daily claims for a month, C20's per-run bounds, C21's full reads and C48's harvest budget still hold, and every resolution job still runs first. A run past a bound fails loudly after those jobs. Test: simulate the loans and offers a month of full claims can fund, then run the keeper and load the offers and auction pages.
- <a id="c82"></a>**C82.** Deploy checks extend C22 and C51. The faucet has code at its address-book address on 31611, its MUSD address is the fixed one, amounts and limit are under their caps, and the relayer passes C65. After each production deploy, a POST with a made-up token must come back as the Turnstile refusal, which proves the secret is present and is not an always-pass test secret. One real claim then proves the path end to end, and a preview build's route must refuse.

### Changes to earlier rules
- Wave 1 intro: "no server endpoint that takes user input" no longer holds. There are two endpoints and two server-rendered address routes.
- Wave 1 and Wave 2 "not applicable" lists: SSRF moves to narrow (A36). "Wave 2 adds no server" stays true of Wave 2 only.
- C20: the keeper's role check also covers the faucet and refuses if its key is the relayer.
- C21: address-book writes now include the faucet. The test-wallet bundle check extends to the relayer key and Turnstile secret (C65).
- C22 and C51: extended by C82.
- C49: "chain id, contract address and id" also governs quest logs (C67).
- Untouched: every contract rule. No existing contract changes, and no Doji contract reads the faucet or EXP.

### General standards (Quests)
1. **Primitives over lists.** "May this be sent" is one simulation of the exact call (C62), not a list of pre-checks; it covers state at simulation and does not cover changes before landing, which C55 and C63 bound. Recipient safety is a gas allowance (C55), not a contract-or-wallet test. "Is the secret real" is one live refusal of a made-up token (C82), not a list of Cloudflare test secrets; it does not prove the sitekey is the right one. Two lists stay because no predicate exists: the quest table is closed (what is not in it earns nothing), and Doji's wallets are tied to the seed script (C75) but cannot cover friends.
2. **Normalize before you compare.** One address parser (C66). One log decoder for explorer and RPC (C67). One EXP function in three places (C69). One UTC-day function for `claim` and its view (C56). One way to read BTC (C58). The canonical URL and the cache key come from the same parser (C73).
3. **Validate outputs like inputs.** The hash is computed locally, and success needs a faucet event or `claimed` (C63, C64). Refusals are a closed list (C64). Image text is computed values only (C77). Explorer hashes and cursors are rechecked (C72, C78). Bonus text and links are checked at build (C74). EXP itself is an output a future reward would consume, so it decides nothing today (C71).
4. **Fail closed.** Turnstile down, RPC down, a failed simulation, a gas price over the ceiling or a missing key means no send. Partial logs give no final number. A bad bonus file fails the build. Every outside call has a timeout, and body, token, page count and render have caps. Deliberate limit: a quest or faucet failure stays inside quests. Lending, the keeper and every contract use neither endpoint.
5. **Non-goals.** The quests do not defend against: one person using many wallets (Turnstile, one claim per address and the daily limit slow and cap that, they do not prove one human); a paid solving service beating Turnstile, which can keep claims scarce all day even under C57; a claim for an address the caller does not own, which needs no proof and only gives that address a kit; two wallets of one person completing "a different wallet" or trading units between them; dust actions, which count unless a quest's row says otherwise; a lying explorer or RPC changing the EXP shown, which is why C71 exists; screenshots, fake images and vanity addresses that match a short address (the page shows the full one); X showing a stale card; an explorer outage making quests and the leaderboard unavailable; a stolen relayer key within C65's limit; an owner key compromise, which reaches the whole faucet; faucet funding running out through honest use; a compromise of Cloudflare, Reown, Vercel, GitHub or the wallet app, beyond lockfile pinning; a wallet that hides what it signs; legal terms for any future use of EXP, which do not exist yet.

### Confirmed before C54 to C82 were built
Every quest has an event that names the wallet, or an id that leads to one, so no quest rests on the transaction sender (C68). All of them can be read per wallet through indexed topics, with follow-up reads by tokenId, offerId or listingId. MUSD refuses its own address as a recipient; a Safe-style receive needs about 6,300 gas, well inside RECIPIENT_GAS. Turnstile's reply carries `success`, `hostname` and `action`, a made-up token is refused with `bot_check_failed`, and the IP comes from `x-vercel-forwarded-for`. The public RPC reports pending nonces, and can return null for a mined transaction, so the browser re-reads `claimed` (C64). The explorer allows about 300 calls a minute. Reown's allow-list is left open (C79).
