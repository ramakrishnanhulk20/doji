# Doji threat model

Written at the architecture gate on 2026-10-16, before any contract code, following the threat model pass in our build method (taken from the Monad Foundation's "Writing secure code with LLMs"). The system was described in plain functional terms first; an independent reviewer produced sections A, B and C from that description, in two passes: one for a pooled-vault design, then a full second pass for the fixed-term credit-market design we chose. Section C is the definition of done: a contract is finished only when every invariant in C is upheld and a test shows it.

**What Doji is.** Holders of veBTC (Mezo's vote-escrow Bitcoin position, an ERC-721) hand the position to `LoanManager` and borrow MUSD for a fixed term at a fixed rate from lenders who post offers in `CreditMarkets`. Each loan date ("maturity") is a Thursday 00:00 UTC and is its own market. Lenders receive ERC-1155 credit units for that date (one unit is one MUSD due on that date), which they can transfer. A loan that becomes unsafe or goes unpaid is sold in an auction; if nobody buys, the lenders receive the Bitcoin itself. A keeper script that anyone can run triggers resolutions. The contracts cannot be upgraded. There is no database and no server endpoint that takes user input.

**Context we do not hide.** On 2026-10-05 an attacker moved 37 veBTC positions on Mezo mainnet through a trusted-forwarder (meta-transaction) sender-check flaw (https://mezo.org/blog/incident-report-october-5-2026). Meta-transactions on veBTC are now disabled. A contract that holds many veBTC positions concentrates exactly that kind of risk, which is why custody comes first below.

## Design findings and how each was settled

Findings from both passes. "Ram" means it changes who gets paid what when something goes wrong, so the founder decided it.

| # | Finding | Ruling | Invariant |
|---|---|---|---|
| F1 | A sale priced off the debt hands the borrower's spare value to the buyer | Ram: the auction starts at the full BTC value and the borrower keeps everything above debt plus a stated penalty | C11 |
| F2 | An expired loan had two endings and whoever called first picked | One state machine (Active, Auction, Closed); settle runs only after an unsold auction and a lock end | C9, C12, C13 |
| F3 | A vote in the lock's final epoch blocks the reset that settle needs | No vote at or after `lockEnd - 1 week` | C5 |
| F4 | A grant manager can pull a grant-backed position out | Collateral must be NORMAL escrow with `grantManager(tokenId) == address(0)` (read from the live verified source) | C2 |
| F5 | A plain transfer in lets whoever registers first become the borrower | `LoanManager` pulls the position itself | C1 |
| F6 | (pooled vault only, superseded by the credit-market design) | Successor is per-market accounting | C14, C15 |
| F7 | The owner could change terms on live loans | Terms snapshotted per loan (since the audit, the auction floor, penalty and duration too) and copied into each auction | C19 |
| F8 | A permanent lock reports `end = 0` and would look expired | Confirmed in the live source; a permanent lock is never expired | C6 |
| F9 | With few bidders, a borrower or friend could buy the position back below the debt and leave lenders short | Ram: the auction floor never goes below min(debt, start value) | C29 |
| F10 | One unresolved loan could freeze a whole date's payouts, for example if a forced DEX sale cannot meet its minimum | Ram: if nobody buys, the lenders receive the Bitcoin itself at the oracle price; no DEX sale exists, and every loan closes within a published time limit | C12, C26 |
| F11 | Minting credit units calls the lender's receiver hook in the middle of a borrow | Units are recorded in storage and the lender mints them later | C23 |
| F12 | The fee had no way out and no ranking against lenders | Ram: the fee is minted as treasury units at the same date, so the protocol shares any loss pro rata with lenders and no MUSD is ever stuck | C25 |
| F13 | Fill rules were unstated, so an offer for one date could fund a loan at another | Each listed offer must be open, for exactly the loan's date, at or under the borrower's maximum rate, and filled for exactly the listed amount | C8 |
| F14 | An auction on a loan that recovers keeps falling from its old start price | Ram: a loan that is safe again returns to Active; the next trigger starts a fresh auction | C11 |
| F15 | A reward claim measured by balance change could include another position's BTC | Tokens Mezo pays to `LoanManager` through permissionless calls are refused as reward tokens; the borrower's own `claim(tokenId)` is credited to that tokenId only | C10 |
| F16 | A pause just before a due date would block rolling and force honest borrowers into default | Ram: rolling is never paused | C19 |
| F17 | The settle split was unstated | Settled by F10: the same penalty as a sale, taken in BTC; the borrower gets the rest | C12 |
| F18 | Per-fill rounding could make units differ from debt | One quote function; maker units plus treasury units equal the face exactly; interest per second | C8, C14 |
| F19 | A first-caller setter linking the two contracts could be front-run | Each contract fixes the other's address in its constructor | C27 |
| F20 | (upgradeable option only) | Not applicable: Ram chose immutable contracts | C19 |
| F21 | (audit M-01) An auction priced only from its start value sold a recovered position below the debt, and the borrower could buy it back cheap | Ram: every purchase reprices at a fresh value and never pays less than the floor at the value now, so the market gets at least min(D, value now) and a rebound raises the price for the borrower | C11, C29 |
| F22 | (audit L-01) The owner could change the auction terms of a loan already open | Floor, penalty and duration are snapshotted per loan when it opens or rolls | C19 |
| F23 | (audit L-02) A roll could pay out new MUSD while borrows were paused | While paused, a roll may refinance or top up but pays nothing out; rolling itself is still never paused (F16) | C19 |
| F24 | (audit) A treasury address that refuses MUSD or BTC could block every sale and settle | Penalties are credited to the treasury as claimables it collects through `claim()` | C3, C28 |
| F25 | (review) One unpaid loan kept every lender at its date out of their money for up to about 5 weeks | Ram: from the date, lenders withdraw their share of what has been collected so far, again as more arrives; only the share still owed by open loans waits | C14, C15, C26 |

Checked in the live verified veBTC source on 2026-10-16: permanent locks report `end = 0`; `depositFor` is open to anyone on normal positions and only raises the locked amount; voted positions can be transferred; grant-backed positions are marked by `grantManager(tokenId)`; mainnet `locked()` returns `amount, end, isPermanent, boost`, testnet the first three. To confirm by fork test before the invariants that depend on them are final: whether `poke` counts as a vote; whether the fee distributor's `claim(tokenId)` is permissionless and where it pays for an expired lock; whether `veBTC.withdraw` pays native BTC by a call; whether PoolsVoter blocks votes in the first or last hour of an epoch; that epochs start at `t % 604800 == 0`; whether BoostVoter sets the veBTC voted flag.

## A) App-class risk profile

Class: a custodial fixed-term credit market. It runs an order book that escrows lender MUSD and issues transferable claims (ERC-1155 credit units) that redeem pro rata from a per-maturity pool. It holds other people's bearer collateral (veBTC NFTs) and acts as their owner toward Mezo contracts. It prices loans with an external oracle and lets anyone force-sell or wind down collateral. Four sub-classes stack: an escrow order book; an issuer of claim tokens with pro-rata, loss-sharing redemption; a custodian acting as owner for many users (confused-deputy territory); and an oracle-priced liquidation engine that anyone can trigger.

- **A1 Collateral identity and custody.** The NFT enters by `deposit` (pulled with `transferFrom`) or `lockAndDeposit` (minted to `LoanManager` by `createLockFor`, so there is no prior owner). A plain transfer in by someone else runs no hook and must never create a position. `onERC721Received` hands over an operator, a `from` and free-form data, and only `from` is the prior owner.
- **A2 Collateral that changes or leaves without the custodian acting.** Grant managers can revoke and move grant NFTs. Managed escrows let depositors pull value out. veBTC is a proxy Mezo can upgrade. The 2026-10-05 forwarder incident shows that one sender-check flaw moves NFTs without the owner, and holding every NFT in one address turns one such flaw into a loss for every maturity at once.
- **A3 Valuation, parsing and clock mismatch.** Borrow, roll and liquidation read `locked()` and `fetchPrice()`. `locked()` returns 3 fields on testnet and 4 on mainnet, the amount is a signed int128, a permanent lock reports `end = 0`, and voting power decays and is not the locked BTC. Offer maturity, loan maturity, lock end and epoch are compared against each other, and seconds to maturity sit inside the face formula. If any two go through different arithmetic, a loan can outlive its lock, roll after default, or owe a different face from the units minted for it.
- **A4 Oracle dependence.** A stale or zero price must stop borrowing. The same price starts both kinds of auction and splits the Bitcoin in settle, so an oracle outage stalls resolution and the market's finalisation. MUSD = 1 USD is assumed and never checked.
- **A5 Liquidation economics.** The sale starts at collateral value and falls to a floor. In a thin market the only bidder may be the borrower or a friend. An auction on a loan that recovers must not keep running on an old start value.
- **A6 Confused deputy.** Every Mezo contract trusts `LoanManager` as owner of every NFT at once. One missing per-token check in a pass-through (vote, reset, poke, claimFees, claimBribes, claim, increaseUnlockTime) lets anyone act on another user's NFT. `claimFees` and `claimBribes` take reward-contract and token addresses chosen by the caller, so attacker code runs in the middle of `LoanManager`'s call.
- **A7 Reentrancy, receiver hooks and balance deltas.** Minting ERC-1155 units would call the maker's `onERC1155Received` in the middle of a borrow or roll. NFT transfers out, BTC paid out and reward forwarding hand control to outside code mid-update. `LoanManager` holds claimables at rest, so forwarding by raw balance would sweep them, and a measured delta can still catch another position's BTC if a third party can make Mezo pay `LoanManager` during the call.
- **A8 Claim-token accounting.** Units are a pro-rata claim on a per-maturity pool of MUSD and, after a settle, BTC. When units differ from debt, a fully repaid market redeems below 1 or leaves funds stuck. Escrow and every market's collected funds share one balance, so a bookkeeping slip moves money between makers and maturities. If the open-loan counter drops twice the market finalises early; if it never drops the market freezes. Losses at a maturity are shared by every unit there, including units from loans a lender never chose.
- **A9 Liveness.** One unresolved loan blocks a whole maturity. A vote in the lock's last epoch blocks the reset. A permanent lock needs a reset, `unlockPermanent` and up to 28 days. `increaseUnlockTime` lets a borrower push the lock end out before defaulting. A stale oracle stops auction starts and settle. A hostile maker hook, a recipient that reverts, unbounded arrays or a pause that blocks roll can each stop a flow.
- **A10 Privileged roles.** If the owner could change the liquidation line, curve or fee on live loans, it could hurt borrowers or lenders. A pause that stops repay, cancel or redeem traps users. Because the contracts are immutable, no admin can replace code; the cost is that a bug or a Mezo change (for example to `locked()`) cannot be fixed in place, and the only answer is to pause new risk and launch a new deployment that users move to themselves.
- **A11 Approvals and signatures.** A function that pulls from an arbitrary `from` spends a victim's standing approval. A front-run permit makes honest calls revert. A UI that asks for `setApprovalForAll` on veBTC or on credit units exposes every NFT or every maturity the user holds.
- **A12 Off-chain.** The keeper and the web app read a public RPC and sign. With no database, the UI rebuilds the offer book from events, so spam offers, hostile contract makers and offers cancelled in the same block all reach the borrower's transaction. Reward token names are strings an attacker picks. Signing on the wrong chain (31611 versus 31612) or against a wrong address book sends assets to the wrong place. GitHub Actions secrets leak if pull-request code runs with them.
- **A13 Order-book races.** A maker can cancel ahead of a fill, another borrower can take the same offer, and a borrow can cite an offer from a different maturity. Each of these must revert, and none may fill on different terms.

Not applicable: SSRF; SQL, command or template injection; file upload; path traversal; sessions and cookies; multi-tenant database isolation. There is no database, no server endpoint that takes user input and no stored user content. Per-tokenId and per-maturity isolation inside the contracts stand in for tenant isolation (A6, A8). On-chain price manipulation does not apply: the price comes from the Skip oracle, not from a pool this system reads, and Doji never swaps on a DEX. Bridging is out of scope.

## B) Threat model

**Trust boundaries**
- T1 Any EOA or contract calling `LoanManager` or `CreditMarkets`, including `onERC721Received`.
- T2 Answers from Mezo contracts: veBTC (`locked`, `ownerOf`, escrow type, `grantManager`, voted state, minted tokenId), PriceFeed, PoolsVoter, BoostVoter, the fee distributor.
- T3 Outside code our contracts call or pay: reward contracts and tokens, ERC-1155 receivers, and contract recipients of NFTs, BTC or MUSD.
- T4 `LoanManager` and `CreditMarkets`: each takes the other's numbers (fills, faces, credits) as fact.
- T5 Mezo governance: the code behind the veBTC proxy can change.
- T6 The owner, guardian and treasury keys.
- T7 Mempool and block producer: transaction order, timestamps, the maturity instant, epoch edges.
- T8 Public RPC feeding the keeper and UI; GitHub Actions feeding the keeper; npm and Vercel feeding the bundle; the UI feeding the user's wallet.

**Attacker-controlled inputs**
- Direct: tokenId; offer maturity, APR and amount; `offerIds[]`, `amounts[]`, `maxAPR` and maturity in borrow and roll; repay amount and target tokenId; lock amount and duration; `pools[]`, `weights[]`, `rewardContracts[]`, `tokens[][]`; purchase `maxPay` and deadline; redeem amounts; unit transfers; NFT transfer operator, from and data; permit fields; `msg.value`; `msg.sender` being a contract with ERC-721, ERC-1155 or token hooks; timing relative to the keeper, the maturity instant, the epoch flip and the lock end.
- Indirect: what `locked()` returns (layout, sign, permanent flag, and end, which the borrower can push out with `increaseUnlockTime`); `ownerOf`; escrow type; grant manager; voted state; lock amount (`depositFor` is open on normal positions); price value, decimals and freshness; how reward contracts and tokens behave; permissionless Mezo calls that pay `LoanManager` as owner; the offer book (hostile contract makers, offers cancelled in the same block); unsolicited MUSD, BTC, units or tokens; stored values read back later (borrower, maturity, face, repaid, open-loan count, collected, auction snapshot, claimables, a returning tokenId's leftovers); owner parameters; RPC answers and event logs; token names; the wallet's chain ID.

**Privileged position and assets**
- `LoanManager` owns every collateral NFT and so all locked BTC. It is the only address Mezo accepts to vote, reset, extend, claim, `unlockPermanent` or withdraw them, so one veBTC sender-check flaw reaches all of them at once.
- `LoanManager` is the only caller that can open loans against escrowed offers and credit a market, so it decides what each market is owed.
- `CreditMarkets` holds every maker's unfilled MUSD and every maturity's collected MUSD and BTC in one balance, and it is the only minter of units. Isolation between maturities is bookkeeping, not separate contracts.
- `LoanManager` holds borrower claimables (auction surplus in MUSD, settle leftovers in BTC) between transactions.
- The owner controls parameters and the treasury address; the guardian controls pause; the treasury receives fee units and penalties. The keeper key holds gas only. The UI decides which offers, transactions and approvals users are asked to sign.

**Attacker goals**
- G1 Borrow more than the collateral is worth, then walk away: misdecoding `locked()` across chains, valuing by voting power, a grant or managed NFT losing value or leaving custody, price decimals, a maturity past the lock end, a raised maxLTV.
- G2 Take another user's NFT or funds: claiming a raw-transferred NFT, a pass-through or `withdrawCollateral` without a borrower check, two endings both completing, a stale record on a returning tokenId, a reward delta that includes another position's BTC, a claimable paid twice, a veBTC flaw.
- G3 Strip borrower equity: a sale on a stale start value, an auction started on a price dip, a curve or penalty changed mid-auction, liquidating a permanent lock whose end reads 0, a pause that blocks a roll.
- G4 Take value from lenders and unit holders: a fill booked to the wrong maturity, units that exceed debt, re-entering cancel inside a fill, buying back one's own collateral below the debt, redeeming before final, finalising while a loan is open.
- G5 Freeze funds: one loan that never closes (oracle down, a vote in the last epoch, a lock pushed out), a hostile maker hook that reverts every fill, recipients that revert, unbounded arrays, a pause on exits.

## C) Defensive-programming standards (the definition of done)

### Custody and identity
- **C1.** Only the address that owned a veBTC just before it entered `LoanManager` can become its borrower: `msg.sender` for `deposit` (which pulls with `transferFrom` after a single-token approval) and for `lockAndDeposit` (which mints with `createLockFor`). Operator and data never set identity. An NFT that arrives any other way, or an `onERC721Received` call from anything but the veBTC proxy, never becomes a position. Test: Alice plain-transfers an NFT in; Bob tries every entry point and cannot claim it.
- **C2.** `LoanManager` accepts only NFTs whose value no third party can lower or remove: one positive test (normal escrow type and `grantManager(tokenId) == address(0)`), checked at intake and on every borrow and roll. If `ownerOf` stops being `LoanManager` while a loan is open, nothing that touches the position runs for that loan, and anyone can close it in one call as a write-off with zero recovery, so its market can still become final (C15). Repaying stays open, because paying a debt only adds to what that date's lenders collect.
- **C3.** `LoanManager` acts as owner only through the calls in this design. It gives no veBTC approval or approval-for-all, has no generic call or multicall, never calls merge, split or `lockPermanent`, and accepts no meta-transactions. Its only delegatecall target is the PassThrough library linked at deploy: deployed by the deployer before `LoanManager`, its address embedded in `LoanManager`'s code, its runtime code hash checked against the compiled artifact by the deploy (C22), stateless, unable to self-destruct on Mezo (SELFDESTRUCT is disabled since mezod v13), and run only inside `LoanManager`'s lock after the C4 check. Every call target except the reward contracts in C10 is fixed at deploy. The treasury is the only address the owner may change, and it can only ever receive fee units and penalties; penalties are credited to it as claimables it collects itself, so a treasury that refuses a token cannot block a sale or settle. Ownership cannot be renounced, so the C19 rescue paths always have an owner. The owner's two rescue functions are bounded in C19.
- **C4.** Every borrower action passes one shared check: the caller is the position's recorded borrower. `borrow` also needs the position held with no open loan. Every pass-through needs the position in custody and never runs while the loan is in auction. `vote` and `extendLock` also need the loan to be None or Active, on time and safe at a fresh price, because they change what backs the loan. `resetVotes`, `claimRewards` and `claimRebase` run at any health, because they only clear votes or pay the borrower rewards that are not collateral. `roll` needs the loan Active and not overdue; a loan that is unsafe but on time may roll, because the new loan must pass maxLTV at a fresh price and the old debt is repaid in full in the same transaction. `withdrawCollateral` needs no open loan and sends the NFT only to the recorded borrower.
- **C5.** No vote is cast at or after `lockEnd - 1 week`, and the same applies to `poke` if poke counts as a vote. This guarantees a reset is available to settle when the lock ends. A vote cast before deposit, on PoolsVoter or on ValidatorsVoter (veBTC counts both through its secondary-voter list), is cleared by `prepareSettle`, which resets every voter that holds a live vote for the position; each needs a new epoch since that vote, which C26 allows for. A permanent lock may vote in any epoch, so its settle may wait one epoch for the reset; that wait counts toward C26's time limit.

### Valuation and terms
- **C6.** One function gives collateral value to borrow, roll, liquidation, settle, the keeper and the UI. It decodes `locked()` with the layout of the veBTC deployed on that chain and reverts on any other return size or on a zero or negative amount. It uses locked BTC, never voting power. A permanent lock is never expired, whatever `end` says. Test: fork tests on 31611 and 31612 against known tokenIds.
- **C7.** One function gives price: `fetchPrice()`, above zero, normalised to 18 decimals once. If it reverts or returns 0, then borrow, roll, both auction starts, purchase and settle all revert. Nothing runs on a cached price.
- **C8.** One quote function turns principal, APR, seconds to maturity and fee share into the fill's face, the maker's units and the treasury's units, with maker units plus treasury units equal to the face exactly. Interest accrues per second. A loan's debt is the sum of its fills' faces, fixed at origination; repayments reduce what is still owed, never the face. A borrow, and the borrow half of a roll, succeeds only if all of these hold: every listed offer is open, is for exactly this maturity, has an APR no higher than `maxAPR`, and fills for exactly the listed amount; the maturity is valid and open (C24) and no further away than the maximum term; for a normal lock the maturity is at or before the C6 lock end, and for a permanent lock it is within the maximum term; total face is at most maxLTV times value; principal is at least the minimum loan; the array cap (`MAX_FILLS` offers per loan) holds; the collateral passes C2. Every borrow entry point goes through this one internal path.

### Resolution
- **C9.** A position (custody and borrower) and its loan (maturity, face, repaid, state) are separate records. A loan is Active, Auction or Closed, and exactly one ending completes: full repayment (including by roll), purchase, settle, or the C2 write-off. A loan is Closed in the same transaction that pays its last debt, and its market's open-loan count falls exactly once. The loan record is deleted on close and the position record when the NFT leaves, so a returning tokenId starts empty. Repaying in full during an auction ends the auction, and the NFT stays in the borrower's position.
- **C10.** Reward forwarding runs under a reentrancy lock and pays the borrower exactly the increase in `LoanManager`'s balance of each listed token, measured around the claim. The borrower names gauges, never reward contracts: the fee and incentive contracts are looked up from PoolsVoter (`gaugeToFees`, `gaugeToBribe`) for a gauge PoolsVoter has registered, and every listed token must be on PoolsVoter's own token whitelist. So the only code that runs during a claim is Mezo's own reward contracts paying this tokenId and the whitelisted tokens' own transfer and balance code, and MUSD and BTC rewards, which most pools pay, are forwarded in full. Claimables never change during the call, so a measured increase can never include another user's funds. A token that a stranger can make Mezo pay to `LoanManager` in a separate transaction (the fee distributor's claim on an expired lock) is not credited to anyone (a stated non-goal). The borrower's own `claimRebase` is measured and credited to that tokenId's borrower only.
- **C11.** Let P be the price paid and D the debt still owed. A purchase pays the market min(P, D), the treasury min(penalty x D, P - min(P, D)), and the borrower the rest as a claimable; the three always sum to P. The price follows the curve snapshotted at auction start: the C6 x C7 value at start, falling linearly to the C29 floor over the duration, then flat. Every purchase also reprices at a fresh value: P = max(curve, the C29 floor recomputed at the value now), so a purchase reads the oracle, overdue auctions included. P can therefore rise within a block: anyone can add BTC to a normal lock with `depositFor`, which raises the value now. That only ever raises what the market and the borrower receive, and buyers set `maxPay` with slack (C21). A purchase needs P at most `maxPay` and the deadline not passed. Every step that ends or irreversibly changes a loan (purchase, `prepareSettle`, settle) needs the loan overdue (now > maturity) or unsafe at a fresh price. An auction started while the loan was on time (an LTV auction) sells only while a fresh price shows it unsafe, even after maturity passes; if a fresh price shows it safe, anyone can cancel it, even past maturity, and the next trigger starts a new auction from a fresh value. An auction started after maturity (an overdue auction) can never be cancelled, so a loan restarts at most once. `prepareSettle` may run on an unsafe LTV auction before maturity once its floor time has passed. This is deliberate, because the borrower has had the whole auction to repay, and it is not reversed if the loan later recovers: a permanent lock stays a normal lock of the maximum length and that epoch's votes stay reset.
- **C12.** `settle` runs only when the auction is past its floor time unsold, the lock has ended, and the loan is overdue or unsafe at a fresh price (C11). For a permanent lock, the reset and `unlockPermanent` steps can be called by anyone once the floor time passes. Settle withdraws the BTC and never swaps on any DEX. BTC received is the change in `BTC.balanceOf` around `withdraw`, never `locked().amount`. With V the BTC received valued by C7, the market receives BTC worth min(D, V), the treasury receives BTC worth min(penalty x D, V - min(D, V)) as a BTC claimable, and the borrower receives the rest as a BTC claimable; the three always sum to the BTC received. Afterwards `LoanManager`'s BTC is its claimables plus any stray BTC (C18), which nobody is credited.
- **C13.** Anyone can move an overdue or unsafe loan to Auction, and no single party can stop a resolution. The auction never depends on vote state. NFTs leave by `transferFrom`, never `safeTransferFrom`. No outside code runs inside a resolution (C23). Payouts to users are claimables. Caller arrays are capped. No on-chain loop runs over loans, offers, markets or holders.

### Credit markets
- **C14.** For each maturity, units issued (makers plus treasury; minted, pending, moved into Claims or redeemed) equal the sum of faces of the loans opened in it. A market's collected MUSD and BTC only increase, only by amounts measured arriving from `LoanManager` for a loan of that maturity. Across `CreditMarkets`, MUSD held is at least the open offers' unfilled amounts plus every market's collected MUSD minus paid out (redeemed or withdrawn early), and BTC held is at least every market's collected BTC minus paid out. Escrow pays out only through cancel and fills; collected funds pay out only through redemption and early withdrawal (C15). No accounting reads raw balances, so a donation changes nothing. Test: fuzz posts, fills, cancels, repays, rolls, purchases, settles and redemptions across several maturities, and assert all of these after every step.
- **C15.** A market becomes final only when its maturity has passed (C24) and its open-loan count is 0; after that nothing can add a loan to it. Redemption works only after final: it burns units from `msg.sender` only, first, then pays units x musdAtFinal / faceTotal plus units x btcAtFinal / faceTotal, all fixed at finalisation and rounded down; faceTotal counts every unit ever issued at the date, including units already moved into Claims. Once the date has passed, a holder may also move units into a non-transferable Claim with `withdrawCollected` and take its share of what has been collected so far: min(units, units x collected MUSD / faceTotal) and units x collected BTC / faceTotal, recomputed on the Claim's whole history, and again as more arrives. faceTotal cannot change after the date, so the share only grows, no holder gains by withdrawing first, and a unit receives the same total whichever path or timing, within rounding. Units moved into a Claim can no longer be sold. The MUSD part never exceeds 1 per unit, and paid out (redeem plus withdrawals) never exceeds collected.
- **C16.** An offer's maker, maturity and APR never change after posting, and offer ids are never reused. Posting pulls exactly the amount from `msg.sender` and needs a valid, open maturity within the maximum term (C24), an APR under a hard-coded cap, and an amount at least the minimum offer. Only the maker can cancel, at any time, for exactly the unfilled remainder; no market state or pause can block a cancel. Only `LoanManager` can fill, and a fill cuts the remainder before any other step.

### Funds in and out
- **C17.** Funds are pulled only from `msg.sender`. Repay pulls at most the debt still owed. Roll pulls its top-up only from the borrower. A front-run permit cannot fail a call whose allowance already covers it. `lockAndDeposit` leaves no BTC allowance behind, and the minted tokenId is confirmed as owned by `LoanManager` before it is recorded.
- **C18.** No function is payable. If `veBTC.withdraw` pays by a native call (fork test), `receive()` exists and credits nobody; otherwise there is none. Stray BTC (native or ERC-20), MUSD, units or tokens sent to either contract never become anyone's claimable, any market's collected balance or any offer's escrow.

### Governance and off-chain
- **C19.** The guardian's pause stops only posting offers, opening new loans and lock creation, checked in the internal path those calls share. Roll is never paused: it only takes offers already posted, and blocking it would push honest borrowers into default. While borrows are paused a roll may refinance or top up but may not pay out new MUSD, because that is new borrowing against the collateral the pause protects. The following can never be paused either: cancel, repay, `withdrawCollateral`, auction start, purchase, the reset and `unlockPermanent` steps, settle, finalise, redeem, claims and pass-throughs. Setters keep 0 < maxLTV < liqLTV < 100%, and keep penalty, fee share, APR cap, floor, duration, maximum term, minimum loan, minimum offer and caps inside hard-coded bounds. maxLTV, liqLTV, fee share, auction floor, penalty and duration are snapshotted per loan when it opens or rolls (a roll is a new loan on that day's terms), and each auction copies its loan's terms; a change touches only new offers and loans. The guardian sets no parameters. Ownership moves in two steps and cannot be renounced. The maximum term is at most 4 weeks, within veBTC's 28-day maximum lock, so a permanent-lock loan can never outlive the lock `unlockPermanent` leaves. The admin surface is these setters plus two rescue functions: `rescueToken` moves an ERC-20 only above what is recorded for users (for MUSD and BTC in `LoanManager`, only above the claimable totals; in `CreditMarkets`, never MUSD or BTC), and `rescuePosition` moves only a veBTC that `LoanManager` holds with no position record. The contracts are immutable, and if Mezo changes veBTC the only response is to pause new risk and launch a new deployment that users move to themselves.
- **C20.** The contracts re-check every condition the keeper or UI acts on. The keeper key holds gas only, and the keeper refuses to send anything when its key is the owner, pending owner, guardian or treasury of either contract. Its workflow runs only on main and never runs code from forks or pull requests. It acts on the open loans: a position whose latest `Borrowed` comes after its latest `LoanClosed`, counted from the deployment block, listed by the block explorer as a hint and by the RPC for the blocks the explorer has not indexed yet; when the explorer is down or more than 64 pages behind, the RPC reads only the last 64 pages and the completeness check below is what makes a missed loan loud. For every date it compares the chain's own open-loan count (`marketOf`) with what it found, and a run that finds fewer fails loudly after acting on what it has. Its loops are bounded per run (150 open loans, 32 dates, 20 explorer calls per event, 64 RPC pages), and writes are capped. It simulates every call before sending it.
- **C21.** The UI takes value, LTV, face, debt, liquidation price, auction price and redemption value from the contract views behind C6 to C8, C11 and C15, never recomputes them, and simulates every write. It builds the offer list from events and current offer state, reads a capped number of offers per maturity, skips cancelled or empty offers, and leaves maturity, APR and amounts for the contract to enforce. It sends writes only to addresses from an address book keyed by chain ID, after checking the wallet's chain. It asks for `approve(tokenId)` on veBTC and exact amounts or permit for MUSD and BTC, and never asks for `setApprovalForAll` on veBTC or on units. On-chain strings render as plain text, and unknown tokens are labelled unverified. For each maturity it shows the open loans and their health, so a holder of units can see what backs them. It shows each loan's own auction terms from `loanOf`, never the current settings, and sets `maxPay` and the MUSD allowance with slack, because the price can rise within a block (C11).
- **C22.** A deploy fails unless all of these hold on that chain: every external address has code; `locked()` on a known tokenId decodes as C6 expects and its end is a multiple of 604,800; PriceFeed returns a fresh 18-decimal price; `CreditMarkets` and `LoanManager` each point at the other (C27); and the PassThrough library's runtime code hash equals the compiled artifact's, recorded in the deployment file.

### Credit-market specifics
- **C23.** No outside code runs inside post, cancel, fill, borrow, roll, repay, auction start, purchase, settle or finalise, apart from the fixed Mezo contracts and the reward contracts in C10. Units from a fill are recorded to the maker in storage and minted when the maker calls, so a reverting or hostile maker cannot fail a borrow that lists its offer. Each contract has one reentrancy lock over every state-changing function, and neither contract calls untrusted code while the other is mid-update.
- **C24.** One clock everywhere, with WEEK = 604,800 seconds. A maturity is valid only if it is a multiple of WEEK, which is exactly Thursday 00:00 UTC and the same rounding veBTC uses for lock ends. A maturity m is open for offers and new borrows while now < m. A loan at m can be repaid or rolled without default while now <= m. It is overdue when now > m, and its market can become final only when now > m. The vote cutoff is lockEnd - WEEK. The keeper and UI read all of these from contract views.
- **C25.** The treasury's fee is units at the same maturity, minted at fill beside the maker's. Units therefore equal debt and the treasury shares any shortfall pro rata with lenders. What can remain in a market is rounding dust from redemption and the share of units nobody claims or redeems; `CreditMarkets` never rescues MUSD or BTC, so that remainder stays put by design.
- **C26.** Every loan reaches Closed within a published time after its maturity: the auction duration, plus one epoch for a reset, plus the longest lock the position can then carry (the live `maxLockTime` after `increaseUnlockTime` or `unlockPermanent`). Settle needs no buyer and no DEX, so only an oracle outage can extend it (a stated non-goal). C26 bounds the time a date stays open. Since the review, lenders do not wait for it: from the date, `withdrawCollected` (C15) pays each holder's share of what has been collected, so an unpaid loan delays only its own share, which it can hold for the whole limit, about 5 weeks on a permanent lock and about 4.4 weeks on a normal lock extended to the maximum just before maturity (see the non-goals). Purchase and settle also decode `locked()`, so a veBTC change to its return size would stop every ending except repay and write-off; that is a Mezo upgrade, a stated non-goal. Test: a permanent lock voted in the trigger epoch with no buyer still leaves its market final within the limit.
- **C27.** `CreditMarkets` accepts fills and market credits only from the `LoanManager` address fixed in its constructor (precomputed from the deployer's nonce, or both contracts created by one factory in one transaction). `LoanManager` talks only to the `CreditMarkets` fixed in its own constructor. There is no setter and no initialiser that the first caller can use.
- **C28.** `LoanManager`'s MUSD and BTC balances are always at least the sum of recorded claimables. Each claimable is credited once and paid once, only to its recorded owner, and no settle or reward forwarding touches it.
- **C29.** No purchase pays the market less than min(D, value at the time of sale): every purchase pays at least the floor recomputed at a fresh price, max(floor x value now, min(D, value now)), and never less than the curve from the start value. A loan whose collateral covers its debt when it sells therefore never leaves a shortfall through an auction, a borrower can never buy their own position back below the debt while it covers the debt, and a rebound after the start raises the price for the borrower's benefit. A loan whose collateral does not cover it goes to settle. Tests: the audit's `AuctionNeverReanchors` tests and the fuzz test in `AuditFixes.t.sol`.

### General standards
1. **Primitives over lists.** A valid maturity is one predicate (`t % 604800 == 0`, within range), not a calendar table; it covers every Thursday 00:00 UTC and nothing else, and it does not cover timestamp drift by block producers. Collateral acceptance is one positive test (C2) that refuses any escrow type Mezo adds later; it does not cover a new transfer path an upgrade might add. Authorisation (C4) and pause (C19) each live in one shared path. Fill safety comes from never running maker code (C23), not from an allow-list of EOA makers, because `extcodesize` misses contracts under construction. Reward safety rests on three things together: the measured delta, the reentrancy lock, and no third-party inflow (C10); the last part depends on knowing every permissionless path that pays `LoanManager`, which is list-shaped: it covers the paths confirmed on fork and not one Mezo adds by upgrade.
2. **Normalize before compare.** One `locked()` decoder, one value, one price, one quote function for face and units, one clock (C24) and one BTC reader. Never add `address(this).balance` to `BTC.balanceOf`, because they count the same coins. The debt `LoanManager` records and the units `CreditMarkets` mints come out of the same quote call.
3. **Validate outputs like inputs.** Units are an output that others will price and trade, so mint only what C14 backs. Credits to a market are booked only against funds measured arriving (C14). Rewards and BTC from `withdraw` are measured deltas (C10, C12). Minted tokenIds are checked against `ownerOf` (C17). Events carry the normalised values the keeper and UI act on. The keeper treats RPC data as hints, and the UI renders strings as text.
4. **Fail closed.** Revert on an unknown `locked()` layout, a zero or stale price, a maturity that is not a week multiple, an offer for another maturity, a fill short of its listed amount, an `ownerOf` mismatch or an unknown state. Arrays are capped, keeper loops are bounded, and purchases carry `maxPay` and a deadline. Deliberate exception: exits and resolutions are never paused (C19), because blocking them pushes the loss onto whoever is stuck.
5. **Non-goals.** This system does not defend against:
   - A malicious or compromised Mezo contract or upgrade (veBTC, PoolsVoter, BoostVoter, fee distributor, MUSD, PriceFeed). A veBTC flaw reaches all collateral at once, as on 2026-10-05; the guardian can stop new borrows but cannot reverse a theft.
   - Wrong prices inside the 60-second oracle window, MUSD trading away from 1 USD, or an oracle outage longer than the C26 limit.
   - BTC price moves after a settle: lenders paid in BTC carry that price risk until they sell.
   - Losses shared across a maturity: every unit at that date shares any shortfall, including units held by lenders who never chose that loan.
   - Lenders who want out before maturity: units can be transferred, but the system provides no buyer and no price.
   - Interest after maturity: the face is fixed, and unit holders earn nothing while a late loan resolves.
   - Mempool griefing that only makes a borrow revert (a cancel or another fill landing ahead of it).
   - Keeper uptime: GitHub cron is best effort, and anyone can run the keeper.
   - The value of votes, bribes and boosts, none of which counts as collateral. Rewards a third party pays straight to `LoanManager` are not credited to anyone.
   - Mezo's PoolsVoter trusts an ERC-2771 forwarder. A flaw in that forwarder could act as `LoanManager` on PoolsVoter (vote, reset, claim) and bypass C4 and C5; rewards would still land with `LoanManager`, and the worst outcome is a delayed settle.
   - A secondary voter Mezo adds to veBTC after deployment: a vote there would block settle until Mezo's voter is reset by other means.
   - BTC that a stranger's fee distributor claim delivers for an expired held lock is credited to nobody, and the owner's `rescueToken` can move it, because it sits above the claimable totals. The owner is trusted to return it to that position's borrower.
   - A whitelisted reward token whose own code calls out during a claim could, at most, move value that is credited to nobody into the measured window; it cannot reach claimables or another position's recorded funds.
   - A compromised user wallet or RPC, or an npm or Vercel supply-chain attack beyond lockfile pinning.
   - An owner key compromise beyond the C19 bounds.
   - A settings change inside the C19 bounds that lands just before a borrower's borrow or roll applies to that loan. The setters have no timelock; the UI shows the terms a loan will get (C21).
   - A delay, not a loss, on the share of a date still owed by an unpaid loan: it can wait until the C26 limit (about 5 weeks). Everything already collected can be withdrawn from the date (C15). A Claim cannot be sold; a market for units is planned for Wave 2.
